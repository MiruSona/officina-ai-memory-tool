# 기억이 아니라 상태 관리 — Lemmalog 글에서 가져올 것

- 출처 : GeekNews <https://news.hada.io/topic?id=33015> · 원문 <https://pwning.systems/posts/llm-memory-program-analysis/>
- 읽은 날 : 2026-08-30 (원문 전문 + GN 요약 + 댓글 전부)
- 대상 : `AIMemoryTool/` (mem)

---

## 1. 한 줄 결론

**엔진(Datalog)은 안 가져오고, 문제 정의 하나와 앞단 교훈 둘만 가져온다.**
가져올 것은 **① 무효화 전파(가장 큼) · ② 훅에 「뒤집힌 결정」 보이기 · ③ 골든셋·어간 회귀 시험 앞당기기** 셋이다.

글의 핵심 주장 세 줄 :

1. "기억" 이라 부르는 것은 사실 **찾기(retrieval)** 와 **지금 무엇이 참인가(maintenance)** 두 개고, 벡터 검색은 앞의 것만 한다.
2. 진짜 문제는 사실을 잊는 게 아니라 **전제가 뒤집혔을 때 그것에 기댄 결론이 같이 안 죽는 것**이다.
3. 성능이 0.226 → 0.463 으로 오른 것의 대부분은 추론 엔진이 아니라 **앞단 잡일**(개체 통일 · 날짜 정규화 · 어간 처리 버그 · 검색) 덕이었다.

## 2. 글이 뭘 만들었나 (짧게)

취약점 조사를 오래 하다 보니 LLM 이 **이미 접은 가설을 다시 꺼내고, 틀린 걸로 밝혀진 전제 위에서 계속 생각하더라**는 데서 출발한다.

- **LLM 은 양 끝단만** 맡는다 — 코드·디버거 출력·메모를 `controls(attacker, object_a)` 같은 구조화된 사실로 바꾸는 일, 그리고 결과를 사람 말로 풀어 주는 일.
- **가운데는 Datalog(Lemmalog)** 가 맡는다 — 규칙으로 결론을 뽑고, 무엇이 무엇에 기대는지 기억한다.
- 전제를 철회하면 **거기 기댄 결론이 자동으로 죽는다.** 단, 다른 경로로도 참이면 살아남는다.
- 사실마다 **시간 구간**이 붙는다 : `viable(primitive_a) [10:14, 12:37)` → `not_viable(primitive_a) [12:37, ...)`. 그래서 "지금" 과 "그때" 를 둘 다 물어볼 수 있다.

측정값 (참고용, 우리 일감과 종목이 다르다) :

| 벤치 | Lemmalog F1 | 비고 |
| --- | --- | --- |
| LongMemEval (102문항) | 0.463 ± 0.010 | 문항당 문맥 약 2,700토큰 (전체 넣기 104,000토큰 → **38배 절감**) |
| ㄴ 지식 고치기 갈래 | 0.579 | PropMem 0.528 보다 좋음 |
| LoCoMo (1,986문항) | 0.533 ± 0.001 | 전용 기억 시스템 중 3등 (1등 PropMem 0.605) |
| ㄴ 근거 없는 전제 거부 | 0.707 | 전체 넣기 0.509 보다 크게 좋음 |
| ㄴ 조건부 추론 | 0.164 | PropMem 0.289. **여기가 약점** |
| ㄴ 여러 세션 걸친 추론 | 0.211 | PropMem 0.582. 원인은 추론이 아니라 **사실 추출 실패** |

약점의 원인이 분명하다 — "조용한 식당이 좋다, 단 친구랑 있을 때는 빼고" 같은 **조건부**를 조건 없는 사실로 납작하게 눌러 버려서다.

댓글에서 건질 것 :

- "핵심은 사실을 잊는 게 아니라 **무효화가 전파되지 않는 것**" — 그래서 모든 프로젝트에 **의사결정 로그**를 쓴다는 사람.
- "Claude 로 장기 연구를 하니 **정보 삭제가 제일 어려웠다**. 여러 곳에 적어 두고, 반증된 것도 계속 사실처럼 쓴다."
- "Kubernetes 같은 건 필요 없다. **SQLite 파일 하나나 Markdown 묶음이면 충분**하다. 한 줄에 사실 하나를 `주어 동사 목적어` 로 적으면 git diff 로 검토된다."
- Google 의 OKF 처럼 **LLM 에게 온톨로지를 관리시키는 방향은 오히려 반대**라는 지적. (우리 `2026-08-23-RAG위키온톨로지비교.md` 7절 2번 「OKF 와 칸 이름 맞추기」를 다시 볼 근거)

## 3. 적용하거나 개편하면 좋을 것

| # | 무엇 | 왜 (글의 어디 / 우리 어디) | 기대 효과 | 공수 |
| --- | --- | --- | --- | --- |
| 1 | **무효화 전파** — `mem set <id> --by <새id>` 를 돌릴 때, 그 id 를 `--link` 로 가리키거나 `--sources mem:<id>` 로 근거 삼은 기억을 찾아 **`mem review --kind stale` 큐에 자동으로 올린다.** 자동으로 죽이지는 않는다 | 글의 핵심(전제 철회 → 의존 결론 자동 무효)이고 댓글도 같은 말을 한다. 우리는 지금 **덮인 기억 하나만 죽고 그걸 근거로 쓴 기억은 그대로 산다** (`mem help set` 의 `--by` 는 `superseded_by` 와 `invalid_at` 만 채운다) | 뒤집힌 결정 위에 쌓인 기억이 조용히 살아남는 걸 막는다. 토큰 0 | 3~4시간 |
| 2 | **훅 요약에 「뒤집힌 결정」 한두 줄** — 지금 훅은 살아 있는 것만 밀어 넣는다. "X 로 정했다가 Y 로 바뀜" 을 최근 결정 칸에 짧게 붙인다 | 글의 문제의식 그대로 — LLM 이 **이미 접은 가설을 다시 꺼내는 것**. 우리 훅 상한은 8000바이트라 한두 줄은 들어간다 (`mem help review` · 훅 설계) | 세션이 옛 결정을 다시 제안하는 일이 준다. 토큰 0 | 2시간 |
| 3 | **골든셋 30건과 어간·동의어 회귀 시험 앞당기기** | 글에서 F1 이 0.226 → 0.463 으로 오른 것의 큰 몫이 **`owns` 가 `own` 에 안 걸리던 어간 버그 하나**였다. 우리는 한글 조사·바이그램·`[synonym]` 표까지 있어 같은 종류의 조용한 버그가 날 자리가 더 많다. 골든셋 30건은 지금 「기억이 더 쌓인 뒤」로 미뤄 둔 상태 (README) | 눈에 안 띄는 검색 구멍을 잡는다. 이미 `mem eval` 이 있어 붙이기만 하면 된다 | 손 골든셋 3시간 + 붙이기 1시간 |
| 4 | **역방향 근거 보기** — `mem show <id>` 에 "이 기억을 근거로 삼은 기억" 목록을 붙인다 | 글의 provenance("왜 그때 이게 참이라고 봤나"). 우리는 `--sources` · `--link` 를 앞방향으로만 본다 | 1번의 재료가 되고, 사람이 뒤집을 때 파급을 눈으로 본다 | 1~2시간 (1번과 같이) |
| 5 | **`fact` 에 시작·끝 날짜 명시** — 지금은 `--date`(시작)와 `--invalid-at`(끝)이 따로 있어 사실상 구간인데, `fact` 종류 설명에 "언제부터 언제까지 참" 을 못 박고 `mem show` 가 구간으로 찍는다 | 글의 시간 구간(`[10:14, 12:37)`). 08-30 결정 `20260830-6c3639dc` 로 `fact` 가 막 생긴 참이라 지금 손대기 싸다 | 공유기·회선 같은 환경 사실의 "그때는 맞았다" 를 구분한다 | 1시간 |
| 6 | **검색 문턱 아래면 「관련 기억 없음」 을 분명히** (이미 계획에 있음 — 우선순위만 올린다) | 글에서 **근거 없는 전제 거부 0.707 vs 전체 넣기 0.509** 로 구조화 저장의 가장 큰 승리 자리였다. `2026-08-23-RAG위키온톨로지비교.md` 7절 6번에 이미 적혀 있다 | 지어내기를 줄인다 | 1~2시간 |

권하는 순서 : **1+4 → 2 → 3 → 6 → 5.** 1·4 는 같은 자리를 만지니 한 묶음으로 한다.

## 4. 이미 하고 있는 것

| 글의 것 | 우리 것 |
| --- | --- |
| 철회(retraction) — 지우지 않고 덮는다 | `mem set <옛id> --by <새id>`. 덮은 사실은 `Memory/log.md` 에 남는다 (`Memory/사용법.md`) |
| 출처 추적(provenance) | `--sources` 가 `decision`·`issue`·`caution`·`fact` 에 필수. 접두 다섯(`file:` `commit:` `url:` `mem:` `note:`) |
| 시간 상태 | `--date` · `--invalid-at` · `--stale-after`. 무효한 기억은 검색에서 빠진다 |
| 문맥을 작게 유지 (38배 절감) | 훅이 8000바이트 상한으로 요약만 밀어 넣는다 |
| 모순·낡음을 골라내기 | `mem review --kind conflict,stale,expired,cold,link` — **도구는 판정하지 않고 사람이 한다** (결정 `20260822-dd2b68f3` : 잊기·정리는 LLM 없이 규칙으로만) |
| LLM 은 양 끝단만 (댓글) | 우리는 한 발 더 가서 **앞단도 LLM 이 따로 안 돈다** — 이미 도는 세션이 `mem add` 로 넘긴다. 추가 호출 0 |
| "SQLite 파일 하나 · Markdown 묶음이면 충분" (댓글) | 원본은 `Memory/store/` 의 Markdown, `index.db` 는 언제든 다시 만드는 파생물 (README) |
| 한 줄에 사실 하나 (댓글) | **한 건에 결정 하나** — 두 주제면 거절 (`Memory/사용법.md`) |

## 5. 우리와 안 맞는 것

| 안 가져오는 것 | 왜 |
| --- | --- |
| **Datalog 추론 엔진 자체** | 규칙을 사람이 짜고 계속 관리해야 한다. 우리 일감은 "지난주에 뭐 정했지" 라 여러 단계 추론이 아니다. `2026-08-23-RAG위키온톨로지비교.md` 5-1 에서 OWL·SHACL·SPARQL 을 안 가져온 것과 같은 이유(사람 품) |
| **LLM 이 사실을 술어로 뽑는 앞단** (`controls(...)`, `points_to(...)`) | 토큰이 든다. 우리 제1원칙은 LLM 호출 0 (README 첫 줄) |
| **임베딩 기반 의미 검색** | 글은 이게 큰 개선이라 하지만, 우리는 설치 부담(모델 파일 수백 MB)과 정면 충돌이라 이미 안 넣기로 했다 (`2026-08-23-RAG위키온톨로지비교.md` 2절) |
| **LongMemEval · LoCoMo 로 우리를 재기** | 대화 QA 벤치라 종목이 다르고 한글도 아니다. 우리 자리는 손 골든셋 + `mem eval` 이다. 이미 `20260822-62eef96f` 로 "작성자가 만든 골든셋은 편향" 주의가 걸려 있다 |
| **도구가 알아서 무효화를 전파해 죽이기** | 3절 1번은 **큐에 올리기까지만** 이다. 판정은 사람 몫 — `mem review` 설계 원칙 |
| **조건부 사실을 납작하게 눌러 저장** | 글이 스스로 밝힌 최대 약점(0.164). 우리는 애초에 자연어 본문을 그대로 두므로 이 함정에 안 들어간다. **구조화를 더 밀어붙이자는 유혹을 여기서 멈춰야 한다** |

## 6. 확인한 것 / 못 한 것 · 신뢰도

**확인한 것** — 원문 전문(문제 정의 · 구조 · 철회/출처/시간 · 벤치 숫자 · 약점 · 교훈), GN 요약 5줄, 댓글 전부. 우리 쪽은 `AIMemoryTool/README.md`, `Memory/사용법.md`, `.claude/skills/mem-usage/SKILL.md`, `2026-08-23-RAG위키온톨로지비교.md`, 설계 문서 2개의 목차, `mem help set|review|add` 실제 출력, `mem search` 7회.

**못 한 것**

- Lemmalog 코드나 저장소를 **안 봤다.** 글이 말한 것만 봤다.
- 벤치 숫자를 **재현하지 않았다.** PropMem 이 뭔지도 글에 나온 만큼만 안다.
- 3절 여섯 항목의 공수는 **비슷한 일의 눈대중**이다. `Docs/History/공수기록.md` 를 대조하지 않았다.
- 3절 1번이 실제로 얼마나 걸리는지는 `internal/store`·`internal/index` 코드를 안 열어 봐서 **모른다.** 역참조 색인이 이미 있으면 훨씬 싸진다.
