# keys 칸 측정 — C1 · 기본 (나) 와 (가) 비교

> 2026-10-05 · Opus 서브에이전트 · 설계 `Docs/Design/2026-10-05-자동쌓기와모음기억설계.md` 4-3 · 4-4.
> 저장소 코드에 keys 칸을 넣고, 스튜디오 기억 사본에서 A1 exe 와 C1 exe 를 비교했다.

## 0. 결론 먼저

1. **회귀 0.** keys 가 빈 저장소에서 A1 과 C1 은 v2 · v3 · probe 의 모든 질의에서 결과가 **id · 순위 · 칸까지 같다** (의미 · 낱말 두 모드).
2. **판정 : 자(+2건)에 못 미친다.** keys 를 80건에 달아도 v3 strict r@5 는 (나) +0건, (가) +1건이다. 자는 +2건이다. 자는 안 옮겼다.
3. **오른 것은 MRR 뿐이다.** (나) 는 v3 MRR 을 의미 모드에서 +0.012, 낱말 모드에서 +0.021 올렸다. 이미 5위 안에 있던 답이 위로 올라온 것이다.
4. **기본값은 (나) 로 둔다.** (가) 는 r@5 를 1건 더 올리지만 의미 모드에서 multisession 1건을 10위 밖으로 밀어낸다 (r@10 0.812 → 0.797). (나) 는 놓친 질의를 하나도 늘리지 않았다. 숫자가 (가) 쪽으로 뚜렷하지 않으니 안전한 쪽을 둔다.
5. **권고 : 코드는 남기고, 옛 기억에는 채우지 않는다.** keys 는 선택 칸이다. 비어 있으면 C1 이전과 결과가 똑같다. 검색 품질을 올리는 수단으로 내세우지는 않는다. 「글에 없는 말로 찾고 싶은 기억」에만 다는 손잡이로 둔다.
6. G2 는 의미 모드에서 그대로다 (0.900 · 0.014). 낱말 모드는 오배제가 0 → 0.014 (1건) 로 올랐다. 원래도 못 찾던 질의다. keys 덕에 감쇠를 끈 Raw 검색에는 걸리게 되어 「밀려났다」로 셈이 바뀐 것이다. 새로 놓친 질의는 0건이다 (2-3).

### 2-3. 자 대비 판정

| 자 (설계 4-4) | (나) | (가) |
| --- | --- | --- |
| v3 r@5 +2건 이상 | **+0건 — 못 미침** | **+1건 — 못 미침** |
| G2 안 나빠짐 (의미 모드) | 같음 | 같음 |
| probe strict 오답률 안 오름 | 0.517 그대로 (strict 답이 나온 질의 16 → 16) | 0.517 그대로 (16 → 16) |
| 의미 모드 p95 ≤ 900ms | 93.8 | 105.2 |

- **놓친 질의 수** (v3, 답이 있는데 순위 없음) : (나) 는 두 모드 모두 그대로다 (의미 13 → 13, 낱말 17 → 17, 같은 질의들). (가) 는 의미 모드에서 13 → 14 다. multisession(all) 1건이 10위에서 밖으로 밀렸다.
- **probe 의 답 목록**은 (나) 3건, (가) 5건에서 바뀌었다. strict 답이 나온 질의 수는 둘 다 16 그대로다.
- **낱말 모드 오배제 +1건**은 이미 순위가 없던 질의다. 결과 화면은 그대로다. keys 를 단 답이 Raw 검색(감쇠 끔)에는 걸리게 되어 eval 이 「밀려남」으로 세었다. 놓친 질의 집합은 같다.

## 3. 어떻게 쟀나

| 항목 | 값 |
| --- | --- |
| 사본 | 스튜디오 `Memory\` 를 한 번 얼려 `snap` 으로 떠 두었다. 기억 md **827건**. 판마다 그 사본을 복사하고 `index.db*`·`vectors.bin` 을 지운 뒤 `index --full` 로 처음부터 쌓았다 |
| A1 exe | 작업 트리 A1 판 (C1 편집 전 빌드). 15,134,208 바이트. SHA-256 `02815B7752DD834CBEDAF6463F421C2B77FFA67A9C6473936CB340032D40727F` |
| C1 exe | `.\build.ps1` (설치 없이 `bin\` 까지만). 15,163,904 바이트. SHA-256 `7D5B4BA4D281E2B1A087445D6978BEF89E664A7D44A817BAFB6D3402340FD782` |
| 의미 모드 | 시험용 HOME 에 모델 묶음(`multilingual-e5-small-ko-v2` + onnxruntime)을 두었다. `status --embed` 가 `[낱말+의미]` · 벡터 827건을 확인했다 |
| 낱말 모드 | 빈 HOME. `status` 가 `[낱말]` 을 확인했다 |
| 환경 | `MEM_INSTALL_NO_PATH=1`. `USERPROFILE`·`HOME` 을 시험 HOME 으로 돌렸다. 시험용 뒷문 환경변수는 다 껐다 |
| 셋 | `testdata/golden/goldenset-v2.yaml` (80) · `goldenset-v3.yaml` (81) · `abstain-probe.yaml` (30) |

명령 (판마다 같다):

```
mem index --full --repo <사본>
mem status --embed --repo <사본>
mem eval --no-index --json --repo <사본> --golden testdata\golden\<셋>.yaml
```

(가) 판은 사본의 `Memory\mem.toml` 의 `[search]` 절에 `keys_strict = true` 한 줄을 더했다.

### 3-1. keys 를 채운 절차 — 눈가림

1. 골든셋 v2 · v3 의 `expect` id 만 골라 냈다. **질문 글은 출력하지 않았다.** v2·v3 를 합쳐 답 id 40건이다.
2. 답이 아닌 기억 40건을 씨앗 20261005 로 뽑았다. 80건을 섞어서 id · 제목 · 요약 · 태그 · 본문 앞 800자만 입력 파일로 만들었다. 어느 것이 답인지는 넣지 않았다.
3. 새 Opus 서브에이전트에게 입력 파일 **하나만** 읽게 했다. 골든셋 · testdata · 저장소는 열지 말라고 했다. 시킨 말은 「몇 달 뒤 다시 찾을 사람이 칠 법한, 글에 없는 다른 말 2~4개」다. 에이전트는 기억마다 3개씩 달았다. 글과 겹친 3건은 스스로 고쳤다고 보고했다.
4. keys 를 사본 md 머리말(`tags` 다음 줄)에만 꽂았다. 스튜디오 원본은 안 건드렸다. 색인 때 못 쓴 기억(bad)은 0건이다.

**눈가림 판정 : 질문 유출은 없다.** keys 를 쓴 쪽은 질문을 못 봤다.
단, **어느 기억에 keys 를 달지는 답을 알고 골랐다.** 실제로 쓸 때보다 답 쪽에 keys 가 몰려 있다. 그러니 위 효과는 **위로 부풀었을 수 있다**. 부풀었는데도 자에 못 미쳤으니 판정은 바뀌지 않는다.

## 4. 남은 것

- keys 는 **의미 검색의 벡터 글에는 안 넣었다.** 넣으면 벡터를 다시 만들어야 하고, 넣었을 때의 효과는 따로 재야 한다.
- 옛 기억 약 800건에는 채우지 않았다 (위임 범위 밖). 채울지는 사람이 정한다.
