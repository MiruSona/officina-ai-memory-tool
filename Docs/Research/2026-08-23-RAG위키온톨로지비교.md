## 1. 결론 먼저

| 항목 | 한 줄 정의 | 우리 툴과 핵심 차이 | 가져올 것 | 권장 |
| --- | --- | --- | --- | --- |
| **RAG** | 물어볼 때마다 원본 문서 조각을 찾아 프롬프트에 붙여 주는 방식 | 우리도 넓게 보면 RAG 의 "찾기" 부분만 떼어 쓴 것이다. 다른 점은 **벡터·임베딩을 안 쓴다**는 것 (임베딩은 API 호출=돈, 아니면 모델 파일 수백 MB=설치 부담) | 조각 크기 관리, 하이브리드 순위 섞기(RRF), 답 못 찾으면 "없다"고 말하기 | **부분만.** 벡터는 안 넣음 |
| **OpenWiki** (LangChain) | 코드베이스나 개인 자료를 **LLM 이 읽고 마크다운 위키를 써 주는** CLI | 우리 툴은 **글을 안 쓴다.** 이미 세션이 쓴 기억을 받아 넣고 찾아 줄 뿐. OpenWiki 는 매 갱신마다 LLM API 를 부른다(토큰 발생) | `AGENTS.md`/`CLAUDE.md` 에 위키를 가리키는 줄 넣기(우리도 이미 함), **근거 출처(claims) 딸림파일**, CI 로 자동 갱신 | **안 씀.** 출처 칸만 참고 |
| **llmWiki** (Karpathy 패턴) | 원본을 그때그때 뒤지지 말고 **한 번 정리해 위키로 굳혀 두자**는 설계 아이디어(구현 여럿) | 우리는 "정리해 굳히기"를 LLM 자동화가 아니라 **사람·세션이 `mem add` 할 때 한 줄 요약을 직접 쓰는** 것으로 한다 | `index.md`(한 줄 요약 목록) · `log.md`(시간순 기록) · **lint**(모순·오래된 것·고아 문서 찾기) 세 가지 | **개념만 가져옴.** 자동 편집은 안 함 |
| **온톨로지 · 지식그래프** | 개념과 관계를 정해진 말로 못박아 두는 것 (OWL/RDF/SKOS, GraphRAG, Graphiti 등) | 우리는 그래프를 안 만든다. 대신 **태그 · 범위(scope) · 링크 · 동의어표** 라는 아주 얕은 어휘만 쓴다 | **SKOS 수준의 얕은 어휘 관리** — 태그 표준 목록, 동의어(이미 있음), 상위/하위 태그 | **얕게만.** OWL·그래프 추출은 안 함 |

**한 줄로** : 넷 다 "LLM 을 부른다"는 전제가 깔려 있고, 우리 툴만 **LLM 호출 0** 이다. 그래서 넷을 통째로 가져올 수는 없고, **LLM 이 필요 없는 부분(색인 · 순위 · 검사 · 얕은 어휘)만** 골라 온다.

## 2. RAG

**무엇인가** — 물어보면 → 문서를 잘게 쪼갠 조각에서 관련 있는 것을 찾아 → 프롬프트 앞에 붙여 → LLM 이 그걸 보고 답한다.

**어떻게 동작하나** — 조각내기(chunking) → 벡터로 바꾸기(임베딩) → 벡터 DB 에 넣기 → 질문도 벡터로 바꿔 가까운 것 찾기. 요즘은 낱말 검색(BM25)과 벡터를 같이 쓰고 순위를 섞는 방식이 기본이다.

| 항목 | RAG | 우리 툴 |
| --- | --- | --- |
| 토큰·비용 | 임베딩 API 를 쓰면 넣을 때·찾을 때 둘 다 돈. `text-embedding-3-small` 기준 100만 토큰당 $0.02 [블로그](https://techsy.io/en/blog/best-embedding-models-for-rag) | **0** |
| 설치 부담 | API 안 쓰려면 모델 파일을 받아야 한다. 작은 다국어 모델도 수백 MB (예 `qmd` 는 GGUF 3개 약 2GB 자동 다운로드) [공식](https://github.com/tobi/qmd) | exe 하나 |
| 서버 | 벡터 DB(Qdrant·Chroma 등)를 띄우는 구성이 흔하다. SQLite `sqlite-vec` 로 파일 하나에 넣는 구성도 있음 | 없음 (요구사항: 로컬 서버 금지) |
| 한글 | 다국어 임베딩이 필요. BGE-M3 · Qwen3-Embedding · `multilingual-e5-small-ko` 같은 것이 쓰인다 [블로그](https://milvus.io/blog/choose-embedding-model-rag-2026.md) | FTS5 바이그램/trigram 으로 처리 (조사A 4-1) |
| 라이선스 | 오픈 모델은 대개 Apache-2.0/MIT. API 는 유료 | — |

**우리가 가져올 것**
1. **RRF 로 순위 섞기** — 지금은 낱말 검색 하나뿐이다. 나중에 "낱말 점수 / 최근성 / 중요도" 를 각각 순위로 매겨 RRF 로 합치면 가중치 튜닝이 거의 없어진다. (조사A 아이디어 2·3 과 같은 결론)
2. **없으면 없다고 답하기** — 검색 결과가 문턱 아래면 억지로 내놓지 말고 "관련 기억 없음" 을 분명히 찍는다. 지어내는 게 신뢰도를 제일 크게 깎는다.
3. **벡터는 안 넣는다.** 넣으면 설치 부담이 exe 하나에서 수백 MB 로 뛴다. 요구사항(설치 없이·배포 쉽게)과 정면 충돌.

> 참고로 **`qmd`**(tobi, MIT)는 우리 툴과 구조가 제일 닮았다 — SQLite 하나에 FTS5 + sqlite-vec, CLI 로 부름, 다 로컬. 다른 점은 npm/Node 22 필요, 로컬 모델 2GB, MCP 서버 옵션, 한글은 기본 모델 커버리지가 약해 다른 모델로 바꿔야 한다는 안내가 README 에 있다. [공식](https://github.com/tobi/qmd)

## 3. OpenWiki (LangChain)

**무엇인가** — `npm install -g openwiki`. 코드베이스를 LLM 이 읽고 `openwiki/` 폴더에 마크다운 위키를 써 준다. 개인 모드는 git·Notion·Gmail·Slack·웹검색 등에서 끌어와 `~/.openwiki/wiki` 에 쌓는다. 별도로 **OpenWiki Brains** 라는 "알아서 모아 오는 기억" 틀도 같이 냈다. [공식](https://github.com/langchain-ai/openwiki) [공식](https://docs.langchain.com/oss/openwiki/overview)

| 항목 | 값 |
| --- | --- |
| 만든 곳 · 라이선스 | LangChain · **MIT** |
| 필요한 것 | Node.js 22+, 모델 공급자 API 키(13곳 지원) |
| 서버 | 상시 서버는 없음. `openwiki visualize` 만 로컬 서버. 코딩 에이전트와는 **MCP 로 붙는다** |
| 결과물 | `openwiki/*.md`, `.claims/` (주장마다 근거 출처), `AGENTS.md`·`CLAUDE.md` 에 가리키는 줄, OKF v0.2 형식 |
| 한글 | 문서에 언급 없음 (확인 못 함) |

**우리 툴과 다른 점** — OpenWiki 는 **쓰는 도구**, 우리는 **담고 찾는 도구**다. OpenWiki 는 갱신할 때마다 LLM 이 코드를 읽으니 토큰이 계속 든다. 우리는 이미 도는 세션이 요약을 써서 넘기므로 추가 호출이 0이다.

**가져올 것**
- **`.claims/` 식 근거 칸.** 기억 한 건에 "이 말의 근거가 어디냐"(파일 경로·커밋·URL)를 적는 칸을 두면 나중에 "이거 아직 맞나" 를 사람이 확인할 수 있다. 지금 우리 머리말에는 없다.
- **OKF (Open Knowledge Format)** — 구글 클라우드가 2026-06 에 낸 규격. "마크다운 + YAML 머리말 + 폴더" 가 전부고, 필수 칸은 `type` 하나. v0.2 에서 출처(provenance)·신뢰(trust)·신선도(freshness)·수명(lifecycle) 칸이 붙었다. [블로그](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing) [공식](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)
  → 우리 `기억파일규격.md` 와 모양이 거의 같다. **머리말 칸 이름을 OKF 와 맞춰 두면** 나중에 남의 도구가 우리 기억을 그냥 읽는다. 값싼 보험이다.

## 4. llmWiki (LLM Wiki 패턴)

**무엇인가** — Karpathy 가 2026-04-04 에 gist 로 낸 **설계 아이디어**다. 제품이 아니다. [공식](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)

- 세 겹 : **원본(안 건드림) → 위키(LLM 이 씀) → 스키마(`CLAUDE.md` 같은 규칙 문서)**
- 세 동작 : **ingest**(새 원본 넣고 위키 10~15쪽 고침) · **query**(위키를 뒤져 답하고, 쓸 만한 답은 새 쪽으로 남김) · **lint**(모순·낡은 주장·고아 문서·빠진 상호참조 찾기)
- 특별 파일 둘 : **`index.md`**(전체 쪽 목록 + 한 줄 요약, 갈래별로) · **`log.md`**(시간순 append-only 기록)
- 검색은 위키가 커지면 `qmd` 같은 로컬 BM25/벡터 검색을 붙이라고 권한다.

**이름이 겹치는 구현들** (전부 이 패턴을 따른 것. 상세는 확인 못 한 것이 많음)

| 이름 | URL | 성격 | 라이선스 |
| --- | --- | --- | --- |
| OpenKB | `github.com/VectifyAI/OpenKB` | `pip install openkb`, LiteLLM 으로 아무 모델. 문서→개념·개체 쪽 컴파일. 웹 UI 는 FastAPI 옵션 | Apache-2.0 [공식] |
| llmwiki (Microsoft) | `github.com/microsoft/llmwiki` | VS Code 확장 | 확인 못 함 [요약] |
| llmwiki (lucasastorian) | `github.com/lucasastorian/llmwiki` | Claude 계정을 MCP 로 붙여 위키를 쓰게 함 | 확인 못 함 [요약] |
| llm_wiki (nashsu) | `github.com/nashsu/llm_wiki` | 데스크톱 앱 | 확인 못 함 [요약] |
| llm-wiki (nvk / tonbistudio / ddsyasas), llm-wiki-compiler, emgiezet/llmwiki | 각 GitHub | 템플릿·컴파일러 판들 | 확인 못 함 [요약] |
| **OpenWiki (kdsz001)** | `github.com/kdsz001/OpenWiki` | 이름만 같은 **딴 것**. Mac/Win 데스크톱 앱, 클립보드 캡처 → 개인 위키. Tauri+SQLite, 로컬 저장 | MIT [공식] |

> **주의** : "OpenWiki" 는 **LangChain 것**과 **kdsz001 데스크톱 앱** 둘이 있다. 우리가 볼 것은 앞의 것이다.

**이 패턴을 까는 목소리** [블로그]/[커뮤니티] — HN 스레드(274점·89댓글)에서 나온 지적이다. 결론에는 안 쓰지만 **우리가 피해야 할 함정 목록**으로는 값이 있다.
- 파일 1,000개쯤 넘어가면 무너진다 / LLM 만 고치게 두면 **틀린 말이 눈에 안 띄게 불어난다**
- 굳혀 둔 위키는 **캐시**다. 캐시는 "다시 만들어라" 신호를 놓칠 때 정확히 거짓말한다 → **낡음 감지가 핵심**
- 자기가 쓴 것을 자기가 인용하는 **닫힌 고리**가 된다
  [블로그](https://proudfrog.com/en/insights/llm-wiki-skeptics-guide) [블로그](https://gnu.support/articles/Why-LLM-Wiki-Is-a-Bad-Idea-A-Critical-Analysis-of-Flaws-and-RAG-Alternatives-124408.html)

**우리 툴과 다른 점** — 우리는 위키를 **안 쓴다(작성하지 않는다).** 그래서 위 함정 셋 중 앞의 둘은 애초에 안 생긴다. 원본이 곧 기억이고, LLM 이 기존 기억을 고쳐 쓰지 않는다.

**가져올 것**
1. **`log.md` 처럼 시간순 append-only 기록** — 우리는 `archive/*.jsonl` 이 비슷하지만 "언제 무엇이 들어오고 무엇이 접혔나" 를 사람이 훑는 파일은 없다. 있으면 좋다.
2. **lint 를 "낡음 감지"까지 넓히기** — 지금 `mem lint` 는 길이·태그·중복·죽은 링크를 본다. 여기에 **① 근거로 적힌 파일이 그 뒤에 바뀌었나 ② 서로 어긋나는 결정이 둘 다 살아 있나** 를 더한다. 둘 다 git 과 링크만 보면 되니 토큰 0이다.
3. **`index.md` 는 이미 있는 것** — 우리 훅이 넣는 덩어리가 이 자리다. 더 안 만든다.

## 5. 온톨로지 · 지식그래프

두 갈래를 나눠 본다.

### 5-1. 고전 온톨로지 (OWL / RDF / SKOS)

- **RDF** 는 "주어-서술어-목적어" 세 토막으로 사실을 적는 형식, **OWL** 은 거기에 "이 개념은 저 개념의 하위다" 같은 **논리 규칙**을 얹어 컴퓨터가 추론하게 하는 것, **SKOS** 는 그보다 훨씬 얕은 **낱말 정리용**(상위/하위/관련/동의어)이다. 검증은 SHACL, 질의는 SPARQL. [블로그](https://atlan.com/know/rdf-vs-owl/) [블로그](https://www.larkinfolab.nl/2026/08/03/what-are-the-most-widely-used-ontology-languages-in-2026/)
- **비용** : 토큰은 안 드는데 **사람 품이 크게 든다.** 개념 체계를 먼저 정하고 계속 관리해야 한다. 30인 회사가 감당할 물건이 아니다.
- **한글** : 형식 자체는 언어를 안 가린다. 라벨에 한글을 적으면 된다.
- **라이선스** : W3C 표준이라 공짜.

**우리 툴과 다른 점** — 우리는 개념 체계를 안 만든다. `--scope`(범위) · `--tags`(태그) · `--links`(연결) · `[synonym]`(동의어) 넷이 사실상 **SKOS 의 가장 얕은 부분**이고, 여기서 더 나가지 않는 것이 우리 선택이다.

**가져올 것** — SKOS 딱 한 겹만.
- **태그 표준 목록**을 두고 `mem lint` 가 목록 밖 태그를 경고한다. (지금 `mem tags` 가 쓰이는 태그를 보여주긴 하지만 표준은 없다) 태그가 제멋대로면 검색 품질이 바로 떨어진다.
- **태그에 상위/하위 한 겹** — `unity` 밑에 `unity-build`, 검색 때 상위로 물으면 하위도 걸린다. 동의어표와 같은 자리(`mem.toml`)에 두면 색인을 안 건드려도 된다.
- OWL·SHACL·SPARQL 은 **안 가져온다.**

### 5-2. LLM 쪽 지식그래프 (GraphRAG · Graphiti · Mem0 graph)

조사A 2-6·2-7·3-1 에 이미 있다. 여기서는 **새로 확인한 것만** 적는다.

- **비용이 문제였다가 많이 내려왔다.** 초기 Microsoft GraphRAG 는 개체·관계마다 LLM 요약을 만들어야 해서 색인 한 번에 수천~수만 달러가 나온다는 얘기가 돌았고, 책 한 권(3.2만 낱말) 색인에 $7 수준이라는 계산도 있다. Microsoft 의 **LazyGraphRAG** 는 요약을 질문할 때로 미뤄 색인 비용을 **일반 벡터 RAG 와 같은 수준**으로 낮췄다. [블로그](https://medium.com/graph-praxis/the-graphrag-cost-cliff-how-33-000-became-33-in-eighteen-months-be1b0fbe37e4) [공식](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/graphrag-costs-explained-what-you-need-to-know/4207978)
  → 그래도 **0 은 아니다.** 색인이든 질의든 LLM 을 부른다. 우리 조건에는 여전히 안 맞는다.
- 그래프가 크게 이기는 자리는 **여러 단계를 건너뛰며 물어보는 질문**과 **"전체적으로 어떤 흐름이냐" 같은 넓은 질문**이다. "지난주에 뭐 정했지" 같은 우리 일감은 낱말 검색으로 충분하다. [블로그](https://cruxdigits.nl/blog/rag-vs-graphrag-2026/)

**결론 유지** — 조사A 의 "지식그래프는 v0.1 에 안 넣는다" 를 그대로 둔다. 바뀐 것은 근거 하나뿐이다 : *비싸서 못 한다* 가 아니라 **LLM 호출이 0이 아니라서 안 한다**.

## 6. 우리 툴의 자리

- 우리 툴은 **RAG 의 "찾기" 절반만 떼어, 벡터 없이 낱말 검색으로 돌리는 물건**이다. 답을 만들지 않는다 — 세션에 붙일 조각만 내놓는다.
- 우리 툴은 **위키가 아니다.** 글을 쓰지도, 고쳐 쓰지도, 합치지도 않는다. 쓰는 일은 이미 도는 Claude 세션이 `mem add` 할 때 한다. 그래서 "LLM 이 자기 글을 자기가 인용하며 조용히 틀려 가는" 문제가 구조상 안 생긴다.
- 우리 툴은 **온톨로지가 아니다.** 개념 체계도 추론도 없다. 태그·범위·링크·동의어라는 **SKOS 의 가장 얕은 한 겹**만 쓰고, 그 이상은 일부러 안 간다.
- 우리 툴만 가진 것은 셋 — **LLM 호출 0**, **exe 하나(설치·서버·MCP 없음)**, **한글 우선**. 넷 중 이 셋을 다 만족하는 것은 없었다.
- 그래서 넷에서 가져올 것은 기능이 아니라 **검사 항목**이다 : 근거 출처 칸 · 낡음 감지 · 태그 표준 · "없으면 없다고 말하기".
