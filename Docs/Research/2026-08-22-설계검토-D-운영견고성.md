# mem 운영·견고성·수명 조사 — "오래 쓰면 무엇이 터지나"

조사 대상 : `AIMemoryTool/` (mem 0.1.0, exe 2026-08-22 16:55 빌드).
이 저장소에 실제로 깔린 상태에서 읽기 전용 명령만 돌려 확인했다.

**한 줄 결론** : 코드 자체는 단단하다. 위험은 전부 **"시간이 지나면서 아무도 안 보는 곳"** 에 있다 —
gc 가 사실상 안 돌고, 아카이브가 git 바이너리로 계속 부풀고, 락 하나 남으면 10분간 조용히 멈추고,
`reindex` 한 번에 사용 통계가 0 이 된다. 지금 205건에서는 전부 안 보이지만 수천 건·여러 기계에서 터진다.

## 1. gc 가 실제로는 안 돈다 (상)

**무엇이 문제** — 평소에 색인을 돌리는 건 SessionStart 훅뿐인데, 훅 경로는 gc 를 부르지 않는다.
gc 는 사람이 `mem index --gc` 를 쳐야만 돈다. AI 는 훅이 알아서 한다고 알고 있으니 아무도 안 친다.

**근거**
- `internal/hook/hook.go:60` — 훅은 `index.Run(...)` 만 부른다. gc 호출 없음.
- `cmd/mem/commands.go:260` — `if withGC && !result.Locked` 일 때만 `gcAfterIndex`. `--gc` 는 기본 꺼짐.
- `internal/index/indexer.go:249` — `GCReady` 는 계산만 하고, `reportIndex` 가 stderr 에 안내 한 줄 찍는 게 전부.
  훅은 `Quiet` 라 그 한 줄도 안 나온다.
- 실제 `mem stats` : `마지막 정리 : 없음`. 205건 쌓이는 동안 gc 는 한 번도 안 돌았다.

**어떤 상황에서 터지나** — 1~2년 쓰면 프로젝트 저장소가 수천 건이 된다.
`warm_count = 1000` 을 넘어도 아무 일이 안 일어나고, 검색은 느려지고, 훅 블록을 고를 후보만 계속 늘어난다.
"gc 임계값을 한 달 뒤 다시 잰다"(mem 의 열린 할일)를 재려 해도 잴 데이터가 안 생긴다.

**보완 방안**
1. 훅이 `startup` 일 때만 gc 조건을 보고, 넘었으면 그 자리에서 돌린다. Cooldown 24시간이 이미 있어 폭주하지 않는다.
   — 위험 : 훅 1초 불변조건(#4)을 깰 수 있다. gc 는 파일 수백 개를 쓴다.
2. 훅은 gc 를 안 돌리되 **`GCReady` 를 주입 블록의 "주의할 점" 한 줄로 올린다.** AI 가 읽고 사람에게 말한다.
3. `mem index` 의 `--gc` 를 기본 켬으로 바꾸고 끄는 쪽을 `--no-gc` 로.

**추천 : 2 + 3.** 훅 안에서 수백 파일을 쓰는 건 불변조건 3·4 와 정면으로 부딪힌다.
"정리할 때가 됐다" 를 AI 가 볼 수 있는 자리(주입 블록)에 올리는 게 이 툴의 설계 사상에 맞는다.

## 2. `archive/*.jsonl.gz` 가 git 추적 바이너리 (상)

**무엇이 문제** — 아카이브는 ① **모든 `add` 의 원본 JSON**(승격 뒤 `store.Archive`)과 ② gc 가 접어 넣은 Markdown
을 같은 월 파일에 gzip append 로 쌓는다. 이 파일이 git 추적이다. gzip 은 델타 압축이 안 되므로
**커밋할 때마다 파일 전체가 새 blob** 이고, 두 브랜치가 각자 add 하면 **병합이 불가능**하다.

**근거**
- 설계개요 1절 : `archive/2026-02.jsonl.gz  ← git 추적`.
- `internal/store/inbox.go` `Archive`/`appendArchive` — 승격된 **모든** inbox 항목이 여기로 간다.
- 실제 git 히스토리의 blob 크기 : `1,542 → 2,361 → 123,289 → 150,274` 바이트. 하루 만에 4판, 누적 277KB.
  같은 시점 `Memory/store` 전체가 834KB 다. **아카이브 하나가 저장소 부피의 3분의 1을 이미 차지한다.**
- `.gitattributes` 없음 (확인함). merge driver 지정도 없다.

**어떤 상황에서 터지나**
- 브랜치 A 와 B 에서 각각 `mem add` 를 하고 병합 → `Memory/archive/2026-08.jsonl.gz` 가 binary conflict.
  git 은 "둘 중 하나 고르라" 고만 한다. 어느 쪽을 골라도 **다른 쪽 기억의 원본 기록이 사라진다.**
  (store/*.md 는 파일 이름이 달라 충돌 안 난다. 아카이브만 터진다.)
- 1년 뒤 : 월 파일 12개 × 커밋마다 전체 재기록 → `.git` 안에 같은 내용의 blob 이 수백 개.

**보완 방안**
1. **월 파일 대신 일 파일(`2026-08-22.jsonl.gz`)** 로 잘게 쪼갠다. 충돌 창이 하루로 좁아지고,
   지난 날 파일은 다시 안 써져서 blob 이 한 번만 생긴다. — 가장 싸다.
2. **아카이브를 gitignore 로 뺀다.** 원본은 `store/*.md` 라는 불변조건 1의 논리를 아카이브에도 적용.
   — 잃는 것 : gc 가 cold 로 지운 기억의 유일 사본이 사라진다 (발견 5 와 얽힘).
3. `.gitattributes` 에 `*.jsonl.gz binary merge=union` 은 **안 된다** (gzip 이라 줄 단위 union 불가).
   비압축 `.jsonl` 로 바꾸면 `merge=union` 이 실제로 먹는다. 부피는 늘지만 병합이 저절로 된다.

**추천 : 1 + 3(비압축 jsonl + union merge).** 텍스트 기억은 원래 잘 압축되지만, 이 정도 크기(수백 KB)에서
gzip 이 사는 이득보다 **"git 이 다룰 수 있는 텍스트"** 라는 이득이 훨씬 크다.
`archive_mb` 상한과 `io.LimitReader` 압축폭탄 방어도 그대로 유지된다.

## 3. 남은 `index.lock` = 10분 침묵 (상)

**무엇이 문제** — 락은 `defer release()` 로만 지워진다. `mem` 어디에도 `signal.Notify` 가 없다(전체 grep 확인).
Ctrl+C·훅 timeout(10초) 강제 종료·전원 차단이면 **defer 가 안 돌고 락 파일이 남는다.**
그 뒤 10분 동안 모든 `mem index`·훅·`mem gc` 는 **아무 말 없이 성공(0)으로 끝난다.**

**근거**
- `internal/index/lock.go` `TryLock` — 락이 있고 10분이 안 지났으면 `taken=false`.
- `internal/index/indexer.go:85` — `!taken` 이면 `result.Locked = true` 로 그냥 반환.
- `internal/hook/hook.go:60` — 훅은 반환값을 아예 안 본다. 조용히 지나간다.
- `internal/index/lock.go` `clearStaleLock` — **PID 가 살아 있는지, host 가 이 기계인지 안 본다.** 시간만 본다.

**어떤 상황에서 터지나**
- 훅 색인이 10초 timeout 에 걸려 Claude Code 가 프로세스를 죽인다 → 락이 남는다 →
  **그 다음 세션 몇 개가 통째로 색인 없이 시작한다.** 그동안 `mem add` 한 것은 inbox 에만 쌓이고 검색에 안 잡힌다.
  AI 는 "방금 남긴 기억을 못 찾는다" 는 증상만 본다. 왜인지 알 길이 없다.
- 세션을 Ctrl+C 로 끊는 건 일상적인 동작이다. 즉 **자주 일어난다.**

**보완 방안**
1. `signal.Notify(SIGINT, SIGTERM)` 을 걸고 락을 지우고 나간다. — 강제 종료(SIGKILL·훅 timeout)는 여전히 못 막는다.
2. `clearStaleLock` 이 **PID 생존 여부**를 같이 본다 (Windows `OpenProcess`, 유닉스 `Signal(0)`).
   host 가 다르면 시간 기준만 쓴다. 죽은 프로세스의 락은 즉시 지워진다.
3. `staleAfter` 를 10분 → 90초로 줄인다. 정상 색인이 1초 안에 끝나는 게 불변조건 4 이므로 10분은 지나치게 관대하다.
4. 락 때문에 건너뛴 걸 **다음 성공한 색인이 알려준다** — `mem stats` 에 "마지막 색인" 이 이미 있으니
   그게 하루 넘게 낡았으면 훅 주입 블록에 한 줄 경고.

**추천 : 2 + 3.** 신호 처리(1)는 가장 흔한 경우인 훅 timeout kill 을 못 막는다.
PID 확인이 진짜 해결이고, 90초는 그 백업이다.

## 4. `reindex` 가 사용 통계를 0 으로 만든다 (중)

**무엇이 문제** — `hit_count`·`last_hit_at` 은 **index.db 에만 있고 `store/*.md` 에는 없다.**
`insertMemory`(`internal/index/rows.go:92`)는 이 두 칸을 안 넣으므로 기본값 0·NULL 이 된다.
즉 **파일이 한 글자라도 바뀌면 그 기억의 조회 이력이 사라지고, `mem reindex` 는 저장소 전체를 0 으로 만든다.**

**근거**
- `rows.go:92` `insertMemory` 의 INSERT 칼럼 목록에 `hit_count`·`last_hit_at` 없음.
- `indexer.go` `indexOne` — 해시가 바뀌면 `dropMemory` → `insertMemory`. 통계는 함께 날아간다.
- `internal/config/config.go` `HitDays: 30` — gc 가 "최근 30일 안에 조회된 건 봐준다" 는 근거로 이 칸을 쓴다.
- (`state` 는 파일 front matter 에 있어서 살아남는다. 대비가 명확하다.)

**어떤 상황에서 터지나** — `mem reindex` 는 exe 를 새로 깔 때·토크나이저가 바뀔 때 정상적으로 쓰는 명령이다.
한 번 돌리면 gc 는 **자주 쓰는 기억과 죽은 기억을 구분할 수 없게 되고**, 다음 gc 에서
자주 쓰던 기억까지 warm 으로 접힌다. 불변조건 1("index.db 를 지워도 완전 복구된다")이 실은 안 지켜지고 있다.

**보완 방안**
1. `hit_count`·`last_hit_at` 을 front matter 로 올린다. — 조회할 때마다 store 파일을 써야 해서 불변조건 2 와 부딪힌다.
2. **통계만 담는 별도 파일**(`Memory/hits.jsonl`, gitignore)로 빼고 재색인 때 다시 얹는다.
   기계마다 다른 게 자연스러운 값이라 git 밖이 오히려 맞다.
3. 불변조건 1 의 문구를 "**검색 가능성**은 완전 복구된다. 사용 통계는 파생물이라 초기화된다" 로 고치고 그대로 둔다.

**추천 : 2.** 지금은 gc 판정에 쓰이는 유일한 "사람이 실제로 쓰는가" 신호라서, 날아가면 gc 설계 자체가 헛돈다.
당장 고치기 부담되면 최소한 3(문서 정정)은 지금 해야 한다 — 지금 문서는 사실과 다르다.

## 5. gc 가 지운 파일이 git 으로 되살아난다 (중)

**무엇이 문제** — gc 의 cold 단계는 `store/*.md` 를 **디스크에서 지운다**(`internal/gc/apply.go` `cool`).
그런데 그 파일은 git 추적이다. 지운 상태를 커밋하지 않으면 다음 `git checkout`·`git stash pop`·다른 기계에서의
`git pull` 로 **그대로 돌아온다.** 돌아온 파일은 다음 색인에서 새 기억처럼 다시 들어간다.

**근거**
- `apply.go` `cool` : `os.Remove(abs)` — git 은 전혀 모른다.
- `indexer.go` `dropMissing` — 파일이 없어지면 행을 지우고, 파일이 다시 생기면 다시 넣는다. 무덤이 없다.
- gc 는 index.lock 만 잡고 git 상태를 확인하지 않는다.

**어떤 상황에서 터지나** — 집 PC 에서 gc 가 돌아 300건이 cold 로 지워졌다. 커밋을 안 하고 회사 PC 에서 `git pull`.
집 PC 에서 `git pull` 하면 지웠던 300건이 되돌아오고, 다음 gc 가 또 지운다. **무한 왕복.**
아카이브에는 같은 기억이 매번 새 줄로 쌓인다(발견 2 와 곱해진다).

**보완 방안**
1. gc 가 지운 목록을 `Memory/tombstones.txt`(git 추적)에 남기고, 색인이 그 목록에 있는 파일은 건너뛰고 지운다.
2. gc cold 를 **삭제 대신 `invalid_at` 표시**로 바꾼다. 파일은 남기고 검색에서만 뺀다. 디스크는 안 줄지만
   Markdown 은 원래 작다 (205건 = 834KB. 2만 건이라도 80MB).
3. gc 실행 뒤 "지운 파일을 커밋해라" 를 크게 안내한다. — 사람 손에 맡기는 거라 제일 약하다.

**추천 : 2.** 이 툴에서 gc 의 목적은 디스크 절약이 아니라 **주입 블록·검색 후보를 줄이는 것**이다.
파일을 실제로 지울 이유가 없고, 지우는 순간 git 과의 궁합이 전부 깨진다. 아카이브 의존(발견 2)도 같이 풀린다.

## 8. 백업이 아무 데도 없다 (중)

## 11. `migrate()` 가 오류를 통째로 삼킨다 (중)

**근거** — `internal/index/schema.go`:

```go
func (d *DB) migrate(from int) error {
    for _, step := range migrations[from-1:] {
        if _, err := d.sql.Exec(step); err != nil {
            return nil          // ← 오류를 nil 로 바꿔 버린다
        }
    }
    if _, err := d.sql.Exec("PRAGMA user_version=" + ...); err != nil {
        return nil              // ← 여기도
    }
    return nil
}
```

주석은 "다른 프로세스가 락을 쥐고 있으면 다음 열기에서 다시 시도한다" 는 의도라고 설명한다. 의도는 맞다.
문제는 **어떤 오류든 똑같이 삼킨다**는 것 — 표가 깨졌든 디스크가 찼든 조용히 "괜찮다" 가 된다.
그리고 `migrations` 슬라이스에 `from-1` 로 접근하는데, `from` 이 0 이면(schema.go 상단에서 걸러지지만)
음수 인덱스로 panic 이다. 지금은 `version == 0` 이 위에서 `create()` 로 빠져서 안 터진다 — **간발의 차다.**

**보완 방안**
1. busy 오류만(`isBusy(err)` 가 이미 있다) 삼키고 나머지는 올려보낸다.
2. 이주 실패 횟수를 `meta` 에 세고, 3번 넘게 실패하면 `mem stats` 가 "색인 이주 실패" 를 알린다.
3. `migrations[from-1:]` 앞에 범위 검사를 넣는다 (`from < 1 || from > len(migrations)+1` → `create` 로).

**추천 : 1 + 3.** 둘 다 몇 줄이다.
