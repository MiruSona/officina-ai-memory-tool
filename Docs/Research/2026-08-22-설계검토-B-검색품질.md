# B — 검색 품질과 한글 처리 조사

대상 : `AIMemoryTool` (mem), 실제 저장소 `Memory/store` 205건.
방식 : 코드 정독 + `mem search` 실험 45건 + `index.db` 를 읽기 전용으로 직접 열어 FTS 표 대조.

## 한 줄 결론

**엔진 자체(바이그램 + trigram)는 두 글자 이상 한글 낱말에서 거의 완벽하다(색인 67/68, 검색 64/64).
문제는 엔진 바깥이다 — 따옴표, 한 글자 낱말, 0건일 때의 안내, 전체 건수 미표시.
그중 셋은 "AI 가 자연스럽게 치는 꼴" 이 조용히 0건이 되는 것이라 실사용 품질을 가장 크게 깎는다.**

## 발견 1 (상) — 따옴표로 감싼 질의가 조용히 구절 검색이 된다

**무엇이 문제** : 셸에서 여러 낱말을 따옴표로 묶어 넘기면(`mem search "훅 성능"`) 인자가 하나로 오고,
`joinQuery` 가 **공백이 든 인자를 다시 따옴표로 감싼다**. 그래서 AND 검색이 아니라 구절 검색이 된다.

```
cmd/mem/read.go:175  joinQuery()
    if strings.Contains(arg, " ") { parts = append(parts, `"`+arg+`"`) }
```

**근거** : 실험 38~40, 1. 같은 글자인데 인자를 나눠 넘기면 결과가 달라진다.

| 친 것 | 결과 |
| --- | --- |
| `mem search PATH 잘림` (인자 둘) | OR 완화 후 5건 |
| `mem search "PATH 잘림"` (인자 하나) | 0건 |
| `mem search 훅 성능` | 5d9ee7df 1위, 2건 |
| `mem search "훅 성능"` | 1건만 |

**왜 문제** : 셸에서 따옴표는 "이건 한 덩어리다" 라는 뜻이지 "붙어 있어야 한다" 는 뜻이 아니다.
사람도 AI 도 여러 낱말 질의를 따옴표로 감싸는 것이 더 자연스럽다.
게다가 구절이 되면 **낱말이 1개로 세어져 AND→OR 완화(`search.go:102` 의 `len(terms) > 1`)도 안 걸린다.**
그래서 "조용히 0건" 이 나온다. 문서(`명령명세.md` 49~54줄)에 적혀 있으나 셸 습관과 정면으로 부딪힌다.

**보완 방안**

1. **구절을 명시 플래그로 옮긴다.** `--phrase` 를 만들고 `joinQuery` 는 늘 공백으로 잇는다.
   장점 : 헷갈림이 사라진다. 단점 : 문서와 기존 습관을 고쳐야 한다.
2. **구절이 0건이면 AND → OR 로 자동 강등하고 그 사실을 결과에 적는다.**
   장점 : 기존 문법을 안 건드리고 "조용히 0건" 만 없앤다. 단점 : 일부러 구절을 친 사람에게는 잡음.
3. 0건일 때 안내문에 "따옴표를 빼고 다시 쳐 보라" 를 넣는다. 가장 싸지만 반쪽이다.

**추천 : 2 + 3.** 강등 한 단계(구절→AND→OR)를 넣고 어느 단계에서 답이 나왔는지 한 줄로 적는다.
`Result.Relaxed` 를 단계 이름으로 바꾸면 형식은 그대로 쓸 수 있다. 1번은 다음 판에서 같이 한다.

## 발견 2 (상) — 한영이 섞인 구절은 구조상 절대 못 맞춘다

**무엇이 문제** : 색인은 `원문 전체 + 한글 구간 바이그램들` 을 **이어 붙여** 저장한다(`stems.go:14 ForIndex`).
그래서 영문 낱말은 앞쪽(원문)에, 한글 바이그램은 뒤쪽(바이그램 덩어리)에 있다.
반면 질의는 `PhraseFor` 가 `AND 교집 집합` 처럼 **영문과 한글 바이그램을 한 구절로 이어서** 던진다.
둘은 색인 안에서 절대 붙어 있지 않으므로 언제나 0건이다.

**근거** : `index.db` 를 직접 열어 FTS 표에 던진 결과 —

```
MATCH '"AND 교집 집합"'  →  0건
MATCH '"교집 집합"'      →  5건     (본문에 "AND 교집합" 이 문자 그대로 있는 기억들)
```

`색인스키마.md:93` 이 정확히 이 불변조건을 적어 놓았다 — "색인용이 만든 것 안에 질의용이 만든 구절이 반드시 들어 있어야 한다."
**한영이 섞인 구절에서 이 불변조건이 깨져 있다.**

**왜 문제** : 코드명·파일명이 한글 설명과 섞인 기억이 이 저장소의 절반 이상이다
(`settings.json 병합`, `gc 임계`, `FTS5 색인`). 그런 구절 질의는 전부 조용한 0건이다.

**보완 방안**

1. **`ForIndex` 를 자리 보존형으로 바꾼다.** 원문을 훑으면서 한글 구간은 바이그램으로, 영문은 그대로,
   **원래 순서대로** 한 줄을 만든다. 그러면 색인과 질의의 토큰 차례가 같아진다.
   장점 : 근본 해결이고 구절 검색 전체가 정상화된다. 단점 : `reindex` 가 필요하고(= `tokenizer` meta 값을 올려야 한다) 색인이 조금 커진다.
2. **섞인 구절은 구절을 포기하고 조각별 AND 로 내린다.** 한글 조각은 구절, 영문 조각은 따로 AND.
   장점 : 색인을 안 건드린다. 단점 : "붙어 있어야 한다" 라는 뜻이 반쯤 사라진다.

**추천 : 1.** 색인은 지워도 되는 파생물이라고 이미 못 박아 두었으므로(`71e604f3`) 재색인 비용이 싸다.
1을 하기 전까지는 2를 임시로 쓰는 것도 된다.

## 발견 3 (상) — 한 글자 한글 낱말은 조사가 붙으면 못 찾는다

**무엇이 문제** : `bigrams()` 는 한 글자 구간을 그 글자 그대로 돌려준다(`stems.go:52`).
그래서 질의 `훅` 은 색인에 **낱말 하나로 떨어져 있는 `훅`** 만 찾는다.
본문이 `훅에서`·`훅은` 이면 색인 토큰도 `훅에서`·`훅에`·`에서` 라서 안 걸린다.

**근거** (실측) :

```
Memory/store 에서 "훅" 이 든 파일          66개
mem search 훅 --limit 100                 49건       ← 26% 유실
FTS 표에 직접 MATCH '"훅"'                  49건
FTS 표에 직접 MATCH '"훅"*' (프리픽스)        66건       ← 정확히 회복
```

빠진 예 : `20260822-1f920282` 은 본문에 `훅에서`·`훅은` 만 있어서 `훅` 질의에 안 잡힌다.
같은 이유로 `방`·`값`·`판`·`락`·`키` 같은 한 글자 낱말이 전부 같은 병을 앓는다.

**왜 문제** : `훅`·`락`·`판` 은 이 프로젝트가 실제로 가장 많이 쓰는 낱말이다.
게다가 **오류 없이 조용히 4분의 1을 빠뜨리므로** AI 가 "그런 기억은 없다" 고 잘못 결론 내린다.

**보완 방안**

1. **한 글자 한글 구간은 프리픽스 질의로 던진다** — `ForQuery` 에서 `"훅"` 대신 `"훅"*`.
   장점 : 실측으로 66/66 회복 확인. 코드 두 줄, 재색인 불필요.
   단점 : `훅업` 같은 오탐이 생기고, prefix 색인이 없으므로(`867bdce5` 결정) 그 낱말만 표를 훑어 느려진다.

## 결과 형식(format.go) — AI 가 읽기에 좋은가

**좋은 점**
- 표 한 장 + 닫는 한 줄. 5건에 약 210~220토큰, 한 줄 약 45토큰. 낭비가 아니다.
- `--budget` 이 뒤에서부터 줄을 잘라 내고 몇 줄 잘랐는지 적는다(실험으로 확인).
- OR 완화가 걸리면 그 사실을 본문에 적는다. 전역 기억은 `[전역]` 으로 표시된다.
- `--explain` 이 stderr 로 점수 분해를 준다. 조사에 실제로 큰 도움이 됐다.

**아쉬운 점**
1. **총계가 없다**(발견 6).
2. **왜 걸렸는지가 없다.** 어느 낱말이 어디서 맞았는지 조각(snippet)이 없어, AI 는 요약 60자만 보고
   `mem show` 를 여러 번 돌려야 한다. `fts5 snippet()` 을 한 줄 붙이면 왕복이 준다.
   (다만 토큰이 늘어난다 — `--snippet` 옵션으로 여는 쪽을 권한다.)
3. **점수가 안 보인다.** 표에 없고 `--explain` 을 켜야 나온다. 1위와 5위가 종이 한 장 차이인지
   압도적인지 AI 가 모른다. 점수 한 칸 또는 `상/중/하` 한 글자면 충분하다.
4. **태그·scope 가 표에 없다.** 좁혀 다시 칠 재료가 결과 안에 없다.
