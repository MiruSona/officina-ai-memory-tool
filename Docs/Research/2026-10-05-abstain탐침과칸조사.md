# abstain 탐침과 칸 조사 — 없는 주제에 strict 답이 어디서 앉나

> 2026-10-05 · Opus 서브에이전트 · **재기만 했다. 검색 코드는 안 고쳤다.**
> 더한 것 : 탐침 셋 `testdata/golden/abstain-probe.yaml` · 그 셋을 읽는 시험 1건 · `측정절차.md` 4절 두 줄 · 이 문서.
> 앞 실험 : `2026-10-05-골든셋v3와점수손잡이실험.md` 2-4 · 4절 1·2번.

## 0. 결론 먼저

1. **탐침 셋 30건을 만들었다** (abstain 29 · 정답 있음 1). 검색을 돌리기 전에 30건을 다 쓰고, 그 뒤 원문 검색으로 답이 있는지만 봤다.
2. **기준값 — 저장소에 없는 주제 29건 중 815건 저장소는 15건(0.517), 206건은 8건(0.276)에 엉뚱한 strict 답이 뜬다.** 의미·낱말 모드가 같다. 15건 중 13건은 상위 5칸을 strict 답으로 꽉 채운다 (상위 5 strict 칸 68).
3. **가설(칸 2 DropWord 탓)은 반만 맞다.** 엉뚱한 strict 답 136건(815 · 의미, 상위 10)은 **칸 0 60건 · 칸 2 60건 · 칸 5 16건**이다. 길은 셋이다 (2절).
   - **칸 0** : 관문이 「맞춰야 할 낱말 수」를 **저장소에 있는 낱말만으로** 센다. 셋 중 하나가 저장소에 없으면 남은 둘의 절반 = **한 낱말**만 맞아도 앉는다 (`Jenkins 빌드 캐시` → `캐시` 하나).
   - **칸 2** : 관문이 없다. 칸 안의 「낱말 하나짜리 표」(`낱말:X`)가 낱말 하나만 맞은 문서를 그대로 strict 로 올린다.
   - **칸 5** : 관문이 없다. 앞머리·쪼갬 조각(`게임패드` → `게임`, `앤` 접두)만 맞아도 strict 다.
4. **규칙으로 고칠 안 세 갈래(9판)를 쟀지만 채택 기준을 다 넘은 안은 없다. 그래서 구현하지 않았다.**
   - 낱말 수 하한(칸 2·5 에도 관문) : 탐침은 줄지만 **v3 r@5 0.768 → 0.551** (정답 15건이 칸 2 의 낱말 하나짜리 표에서 온다).
   - idf 몫 하한 : 탐침 2/29 까지 줄지만 **v3 r@5 0.507**. 긴 질의의 정답도 낱말 몫이 낮다.
   - idf 몫 + 코사인 하한 : 815건에서는 **다 넘는다** (탐침 15 → 6 · v3 r@5 53 → 55 · G2 abstain 0.900 → 1.000). 그러나 **206건 v2 r@5 가 0.761 → 0.716 으로 떨어진다.** 코사인 문턱이 저장소마다 다르고, 낱말 모드에는 코사인이 없어 v3 r@5 가 0.507 로 무너진다.
5. **판단** : 낱말 겹침만으로는 「긴 질의의 정답」과 「없는 주제의 헛답」을 못 가른다. 신호는 의미 쪽에 있다 (4번 셋째 판). 다음은 질의–문서 관련도를 **눈금 맞춘 점수**로 주는 재순위기(cross-encoder) 쪽이다 — 앞 문서 4절 3번과 같은 자리다.

- 낱말 모드 · 206건도 같은 꼴이다 (815 낱말 : 칸0 62 · 칸2 58 · 칸5 16 / 206 : 칸0 17 · 칸2 33 · 칸5 6).
- **가설 판정 : 반만 맞다.** 칸 2 는 60건으로 큰 길이 맞다. 다만 「낱말을 빼다 하나만 남아서」가 아니다 — `dropRankings` 는 남은 낱말이 과반이 아니면 이미 nil 을 낸다. 실제로는 **칸 2 의 `matchRankings` 가 같이 던지는 낱말 하나짜리 표(`wordRanks`)** 가 관문 없이 strict 로 올라온다. 그리고 가설에 없던 **칸 0 관문 구멍(60건)** 과 **칸 5(16건)** 가 있다.
- 칸 0 관문 구멍의 자리 : `coverage.go` `qualified` 의 `need := needOf(len(findable))`. 질의 낱말의 과반이 저장소에 있으면 통과시키고(①), 맞춰야 할 수는 **있는 낱말 수의 절반**(②)이다. 셋 중 하나가 없으면 ②가 1 이 된다.
- 덤 : `A*` 는 영문 한 글자 `A` 가 된다. `oneLetterOnly` 는 한글 한 글자만 봐서 영문 한 글자는 「진짜 낱말」로 센다.
- 덤 : 저장소에 없는 낱말 판정은 넉넉하다 — 앞머리(`오토세이브` → ?)·쪼갬 꼴도 「있다」로 본다. 그래서 `missing_words` 가 비어도 칸 0 관문이 낱말 하나로 통과하는 질의가 있다.

## 3. 고칠 안과 잰 값 (스크래치 사본 · 뒷문)

뒷문 exe 에 환경변수 넷을 달았다 (`scratchpad\memprobe\knob.diff`, 164줄). 끈 판은 기준 exe 와 셋 3벌 모두 값이 같다.

| 뒷문 | 하는 일 |
| --- | --- |
| `MEM_TEST_GATE_ALL=1` / `=2` | 칸 0·1 관문을 strict 칸 전부(2·5)에 / 칸 2 에만 더 건다. 떨어진 문서는 칸 3(느슨)이 그대로 낸다 |
| `MEM_TEST_NEED_LIVE=1` | 관문의 「맞춰야 할 수」를 저장소에 있는 낱말 수가 아니라 **질의 낱말 수**의 절반으로 |
| `MEM_TEST_SHARE=θ` | strict 답이 맞춘 낱말의 **idf 몫**(맞춘 낱말 idf 합 ÷ 질의 낱말 idf 합, 없는 낱말은 idf 최대)이 θ 아래면 꼬리표만 칸 3 으로 내린다. 점수·차례는 그대로 |
| `MEM_TEST_COS=c` | 위에 더해, 질의–문서 코사인이 c 이상이면 내리지 않는다 (의미 모드만) |

- 206건에서 떨어진 정답 : `최근 7일 안에 적은 큐에 직접 쓰는 함정` · `검색 차례가 운에 달리는 문제` · `오늘 못 박은 배포 형태`. 셋 다 질의 낱말 몫이 낮고 코사인이 0.55~0.59 사이다.
- 몫+코사인의 문턱(θ · c)을 0.3~0.5 × 0.50~0.70 으로 훑은 모의 계산(실제 판과 건별로 맞는 것을 확인)에서도 **두 저장소를 같이 넘는 자리는 없었다** (815 에서 탐침을 절반 아래로 줄이려면 c ≥ 0.58, 206 에서 v2 를 지키려면 c ≤ 0.53).

- 「안 잼」은 815건에서 이미 다른 기준에 떨어져 206건을 안 돌린 판이다.
- **need 만 고치면 탐침이 하나도 안 준다.** 칸 0 에서 떨어진 문서가 칸 2 의 낱말 표로 다시 strict 로 앉기 때문이다. 칸 0 구멍과 칸 2 구멍은 같이 막아야 하는데, 칸 2 를 막으면 v3 정답 15건이 같이 빠진다.

**v3 정답 15건이 칸 2 낱말 표에서 온다는 것** — 칸 2 관문 판에서 빠진 정답은 전부 4~8낱말 질의다 (`검색 차례가 운에 달리는 문제` · `한 범위에 결정이 여럿이면 지금은 어떻게 보나` · `secret check bypass inbox pattern` · `최근에 정한 MCP 방침` …). 이 정답들은 질의 낱말 몫이 0.08~0.35 로 탐침 헛답(0.04~0.54)과 겹친다. **낱말 겹침으로는 둘을 못 가른다.** 코사인을 더하면 815건에서는 갈리지만(정답 최저 0.596 · 헛답 대부분 0.59 아래) 문턱이 저장소에 따라 움직인다.

**설계 결정과 닿는 자리** (넣지 않으므로 판단만)

- 칸 2·5 관문은 **결정 29(strict 칸 = 0·1·2·5)** 를 사실상 「칸 2·5 는 관문을 지난 것만 strict」로 고치는 것이다. 29 를 다시 써야 한다.
- 몫+코사인은 결정 29 의 「칸 소속이 곧 자」를 「칸 소속 + 관련도 문턱」으로 바꾼다. 또 **결정 16(모델이 없으면 낱말 모드, 값이 같아야 함)** 과 부딪힌다 — 낱말 모드에서 자가 다르게 돈다.
- 그래서 diff 는 저장소에 안 넣고 `scratchpad\memprobe\knob.diff` 에만 둔다.
