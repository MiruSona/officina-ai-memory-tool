## 1. "많이 쓰인 기억은 남긴다" 가 코드에 없다 — **상**

**무엇** 설계 8-2 면제 목록에 "최근 `hit_days`(30일) 안에 검색 결과로 뽑힌 것(`last_hit_at`)" 이 있고,
검색 점수에도 `0.2×log(1+hit_count)` 가 들어간다. 그런데 이 두 칸을 올리는 코드는 **중복 add 한 곳뿐**이다.

**근거**
- `internal/index/rows.go:133` `bumpHit` — `UPDATE memories SET hit_count = hit_count + 1, last_hit_at = ? WHERE body_hash = ?`
- 저장소 전체에서 `last_hit_at` 을 쓰는 다른 곳 0곳 (`grep`). `internal/search/engine.go:39` 는 **읽기만** 한다.
- `internal/gc/plan.go:31` `AND (last_hit_at IS NULL OR last_hit_at < ?)`
- 명세 : `명령명세.md` 8절 면제 목록 · 2절 점수식

**왜 문제인가** 두 가지가 같이 깨진다.
① gc 면제 조건 하나가 사실상 없는 조건이다 — 아무리 자주 검색되는 `history`·`howto` 도 나이만 차면 접힌다.
② 점수 가산점의 뜻이 바뀌었다. `hit_count` 는 "쓸모" 가 아니라 **"같은 본문을 몇 번 다시 넣으려 했나"** 다.
AI 가 같은 내용을 반복해서 `add` 하면 그 기억이 검색 상위로 올라간다. 자기가 쓴 것을 자기가 밀어올리는 되먹임이다.

**보완**
- **1안 (추천)** 검색이 실제로 돌려준 상위 N건에 `last_hit_at` 을 찍는다. 다만 이러면 읽기 명령이 DB 쓰기가 되어
  "쓰는 프로세스는 하나" 전제가 깨진다. → **락을 잡은 다음 `index` 실행 때 몰아서 반영**하는 식으로 우회한다.
  즉 검색은 `inbox/hits/<id>` 같은 흔적만 남기고(또는 메모리 큐), 다음 색인이 합산한다. Maildir 원칙과 같은 모양이다.
- **2안** 두 칸의 뜻을 문서에 맞춰 **다시 이름 짓는다** — `hit_count` → `dup_count`, 면제 조건에서 `last_hit_at` 을 빼고
  점수 가산점도 뺀다. 구현 부담이 없고 문서와 코드가 즉시 일치한다.
- 어느 쪽이든 **지금 상태(문서는 있다고 하고 코드는 없다)만은 안 된다.**

## 2. gc 가 규모를 못 잡는다 — 78% 가 영구 면제 — **상**

**무엇** `decision`·`issue`·`caution` 은 **나이·건수와 무관하게** 면제다. 열린 `todo`·고정도 면제다.
남는 것은 `history`·`howto`·닫힌 `todo` 뿐인데, 지금 저장소에서 그 셋은 205건 중 44건(21%)이다.

**근거**
- `internal/gc/plan.go:28-32` `exemptSQL`
- `mem stats` : caution 70 · decision 75 · history 26 · howto 11 · issue 16 · todo 7 → 면제 대상 161건(78%)
- 이미 알려진 관련 이슈 : `20260822-437951c7` "D2 5,000건 이상에서 따뜻함 단계가 사실상 없다 … **안 고침**"
- 규모 전제 : `20260822-ed26c588` (프로젝트당 수천 · 전역 1만)

**왜 문제인가** gc 의 목적은 두 개다 — (가) 디스크·색인 크기 줄이기, (나) **검색 잡음 줄이기**.
(가)는 1KB×2만 = 20MB 라 애초에 문제가 아니라고 설계가 인정했다. 그러면 gc 가 실제로 해야 할 일은 (나)뿐인데,
**잡음을 만드는 주범이 정확히 면제 대상이다.** 2년 전 `caution` 70건이 오늘도 만점으로 검색에 섞인다
(`issue`·`caution` 은 감쇠도 1.0 고정). 5년 뒤 `decision` 2천 건이 되어도 gc 는 한 건도 안 접는다.
"함정은 나이를 먹어도 참이다" 는 맞지만, **없어진 부품에 대한 함정은 참이 아니다.**

**보완**
- **1안 (추천)** 면제에 "무효 아님" 을 더한다 — `invalid_at` 이 지난 `decision`·`issue`·`caution` 은 접기 대상으로 본다.
  뒤집힌 결정은 이미 검색에서 빠지므로 접어도 잃는 게 없다. 지금 무효는 2건뿐이지만 뒤집기 흐름을 쓰면 늘어난다.
- **2안** 종류 면제를 **감쇠와 잇는다** — 종류로 자르지 말고 "감쇠 반감기의 3배가 지났고 한 번도 안 뽑혔으면 접는다".
  단 이건 발견 1(`last_hit_at`)이 고쳐져야 뜻이 있다.
- **3안** `caution` 에 `scope` 별 상한을 둔다 — 같은 scope 의 `caution` 이 N건을 넘으면 오래된 것부터 접는다.
- 어느 쪽도 어렵다면 최소한 **`decision`·`caution` 이 무한히 는다는 사실을 설계 문서 위험 표에 적어야** 한다.

## 3. `lint --fix` 가 락 없이 `store/` 를 고친다 — **상**

**무엇** 불변조건 2 : "`store/` 파일을 고쳐 쓰는 것은 `index.lock` 을 잡은 단 하나의 프로세스(`mem index`·`mem gc`)뿐".
`lint --fix` 는 락을 안 잡고 `store/` md 를 다시 쓴다.

**근거**
- `internal/lint/fix.go:20-40` `applyFixes` → `options.Store.WriteMemory(item.Memory)`
- `grep TryLock` 결과 : `internal/gc/gc.go:65` · `internal/index/indexer.go:80,102` 뿐. lint 에는 없다
- 게다가 `internal/lint/fix.go:78` `fixUpdatedAt` 은 **DB 에도 직접 UPDATE** 한다
- 명세 : `설계개요.md` 2절 불변조건 2 · `동시성과안전.md` 2절

**왜 문제인가** `mem lint --fix` 를 돌리는 동안 다른 창에서 세션이 시작되면 훅이 색인을 돌린다.
그때 같은 파일을 한쪽은 다시 쓰고 한쪽은 읽는다. rename 재시도 래퍼가 있어 파손까지 가진 않겠지만,
색인이 **고치기 전 내용을 해시로 확정**해 두면 그 뒤 파일 변화가 mtime+size 가 같을 때 영영 반영되지 않는다
(cp949→UTF-8 재기록은 크기가 바뀌니 대개 걸리지만, 태그 소문자화·CRLF 제거는 **크기가 그대로일 수 있다**).
DB 직접 UPDATE 는 더 나쁘다 — 색인 트랜잭션 밖에서 같은 행을 만진다.

**보완**
- **1안 (추천)** `lint --fix` 도 `index.TryLock` 을 잡는다. 못 잡으면 "지금 색인 중이라 --fix 를 못 한다" 고 알리고
  검사 결과만 낸다(종료 코드는 그대로). 코드 열 줄이면 되고 불변조건이 문자 그대로 참이 된다.
- **2안** 불변조건 2 를 "락을 잡은 프로세스만" 으로 다시 쓰고 lint 를 그 목록에 넣는다. (문서만 고치는 값싼 길)
- 1안을 권한다. 불변조건 문구를 늘리는 쪽은 다음 사람이 또 예외를 더한다.

## 4. 기억을 고치는 길이 없다 + add 가 id 를 안 준다 — **상**

**무엇** 세 개가 겹쳐 하나의 구멍이 된다.
1. `patch` 가 고칠 수 있는 칸은 `pinned`·`status`·`invalid_at`·`links` **넷뿐**이고 본문·요약은 못 고친다.
2. `mem add` 에는 `--links` 플래그가 **없다**.
3. `mem add` 가 찍는 것은 id 가 아니라 **inbox 파일 이름**(`1756...123.4567.1.json`)이다. id 는 승격 때 만들어진다.

**근거**
- `internal/store/inbox.go:28` `PatchableFields` · `internal/index/promote.go:171` `patchFields`
- `cmd/mem/commands.go:38-80` `runAdd` — `links` 플래그 없음, `fmt.Println(i18n.AddDone(name))` 의 `name` 은
  `WriteAdd` 가 돌려준 **파일 이름**
- `internal/i18n/i18n.go:232` `"기억을 넣었다 : %s (색인 대기)"`
- 명세는 다르게 적혀 있다 : `명령명세.md` 3절 "출력 : `기억을 넣었다 : 20260822-9e02d7f1 (색인 대기)`"

**왜 문제인가**
- 요약을 30자 미만으로 잘못 쓰면 `lint` 가 **오류**로 잡는데, 그걸 CLI 로 고칠 방법이 없다.
  사람이 md 를 손으로 열어야 하고, 그건 설계가 상정한 흐름이 아니다(불변조건 2 의 회색지대).
- 한 세션에서 기억 둘을 넣고 서로 잇고 싶어도 **id 를 모른다.** 그래서 `links` 는 실질적으로
  `invalidate --by` 한 갈래로만 만들어진다. 실제로 지금 저장소의 links 사용이 얕은 이유가 이것으로 보인다(추측).
- 문서가 "id 를 준다" 고 적혀 있어 AI 가 그 id 를 기억했다가 `mem show` 에 넣으면 못 찾는다.

**보완**
- **1안 (추천)** **id 를 add 때 확정한다.** `NewID` 를 `mem add` 쪽으로 옮겨 inbox JSON 에 `id` 를 실어 보내고,
  승격은 그 id 를 쓴다. 그러면 add 가 진짜 id 를 찍고, `--links` 도 쓸 수 있고, 문서와 코드가 맞는다.
  중복·합치기로 새 파일이 안 생기는 경우가 남는데, 그건 `mem index` 결과 표에 "합쳐짐 : 예약 id → 대상 id" 로 알리면 된다.
- **2안** id 확정은 그대로 두고, 출력 문구를 사실대로 바꾼다("접수했다 : <접수번호>. id 는 색인 뒤에 생긴다").
  값싸지만 links 문제는 안 풀린다.
- 본문 고치기는 **`mem amend <id> --body`** 를 `op:amend` 인보크로 하나 더 두는 것을 권한다. 규칙은 두 줄이면 된다 —
  ① 원본을 아카이브에 먼저 넣는다 ② 본문을 통째로 갈아 끼운다. 지금도 gc 가 똑같은 일을 하므로 새 기계장치가 아니다.

## 5. "지우지 않는다" 가 끝까지 안 지켜진다 — 중

**무엇** 설계의 큰 약속은 "지우는 대신 무효 날짜를 적는다" 인데 gc 에는 진짜 삭제가 둘 있다.

**근거**
- 차가움 : `internal/gc/apply.go:57-78` `cool` → 세 표에서 빼고 `os.Remove(abs)` — **git 추적 원본이 사라진다**
- 삭제 : `internal/gc/archive.go:171` `purge` → 월 묶음 파일 자체를 지운다 (되돌릴 수 없다고 명세도 인정)
- 아카이브를 **검색할 길이 없다** : `FindArchived(from, id)` 는 **id 를 이미 알 때만** 쓴다
  (`gc/archive.go:110`). `mem search --from-archive` 같은 것은 없다.

**왜 문제인가** 차가움으로 내려간 기억은 "지워지지 않았다" 지만 **찾을 수 없다**. 찾을 수 없는 기억은 없는 기억이다.
`mem show <id> --from-archive` 는 id 를 어딘가 적어 뒀을 때만 쓸모가 있는데, id 를 적어 두는 곳이 바로 mem 이다.
그리고 삭제 단계는 아카이브 월 파일을 통째로 지우므로, **그 달에 접힌 기억 + 그 달에 들어온 모든 add 의 원본 JSON** 이 함께 사라진다.

**보완**
- **1안 (추천)** 차가움에서 `memories` 행을 지우지 말고 **본문만 비운 tombstone 행**으로 남긴다
  (`state='cold'`, 요약·태그·id 는 유지, FTS 에는 요약만). 그러면 검색에 걸리고 `--from-archive` 로 이어진다.
  행 하나 200바이트라 2만 건이어도 4MB 다.
- **2안** `mem search --archive` 를 만들어 월 묶음을 순차로 훑는다. 느리지만 "잃지 않았다" 가 참이 된다.
- 삭제 단계는 **끄는 것을 기본으로** 하는 게 맞다(`archive_days=0` = 안 지움). 지금 조건(365일 AND 1GB)이면
  현실에서 거의 안 걸리므로 기본을 "안 지움" 으로 바꿔도 잃는 게 없고 위험 하나가 없어진다.

## 6. 아카이브가 git 추적 이진 append 파일이다 — 중

**무엇** `archive/YYYY-MM.jsonl.gz` 는 git 추적물인데, gzip 멤버를 계속 이어 붙이는 **이진 파일**이고,
gc 가 접은 것뿐 아니라 **모든 `add` 의 원본 JSON**(본문 통째)이 들어간다.

**근거**
- `기억파일규격.md` 7절 5단계 "원본 JSON 을 `archive/YYYY-MM.jsonl.gz` 에 한 줄로 붙이고"
- `internal/store/inbox.go` `Archive(name)` · `internal/gc/archive.go:57` `appendRecord`
- 실측 : 이 저장소 `Memory/archive/2026-08.jsonl.gz` = **150KB / 205건** (gc 는 아직 한 번도 안 돌았다 — `mem stats` "마지막 정리 : 없음")

**왜 문제인가**
- 같은 본문이 `store/*.md` 와 아카이브에 **두 벌** 있다. 저장소가 사실상 2배다.
- git 은 이진 파일을 델타로 못 줄인다. **한 줄 붙일 때마다 파일 전체가 새 blob** 이 된다.
  205건에 150KB 이니 2만 건이면 15MB 짜리 blob 이 커밋마다 새로 쌓인다. 1년이면 clone 이 무거워진다.
- 한 파일 안에 성격이 다른 두 기록(`op:add` 접수 원본 / `op:gc` 접힌 원본)이 섞여 있고, 삭제 단계는 둘을 구분 없이 지운다.

**보완**
- **1안 (추천)** 두 가지를 가른다. **접수 원본(`op:add`)은 git 밖**(`inbox/done/` 또는 `.gitignore` 된 파일)에 두고,
  **gc 가 접은 원본만** git 추적 아카이브에 넣는다. 승격이 끝난 add JSON 은 md 와 완전히 겹치므로 git 에 남길 값어치가 없다.
- **2안** 아카이브를 월 단위 append 대신 **불변 파일 여러 개**(`archive/2026-08/<id>.md.gz`)로 둔다.
  git 이 새 파일만 추가하고 기존 blob 은 안 건드린다. 대신 파일 수가 는다.
- 최소한 **아카이브 크기가 커밋마다 다시 쌓인다는 사실**을 `동시성과안전.md` 10절에 적어야 한다.

## 7. `howto` 가 gc 로 접힌다 (명세는 아니라고 적혀 있다) — 중

**무엇** 명세 8-3 : "규칙 압축은 **`history` 와 닫힌 `todo` 에만 걸린다** — 면제를 빼고 나면 따뜻함으로 내려오는 것이 그 둘뿐이다."
코드의 면제는 `decision`·`issue`·`caution`·열린 `todo`·고정뿐이라 **`howto` 가 빠져 있다.**

**근거** `internal/gc/plan.go:28-32` vs `명령명세.md` 8절 "규칙 압축" 절

**왜 문제인가** `howto` 는 번호 목록 절차다(`기억파일규격.md` 4절). 앞 5줄만 남기면 **1·2·3번 하다가 끊긴 절차** 가 된다.
게다가 `howto` 는 감쇠 반감기 720일로 `decision` 과 같은 대접을 받는 종류다 — "오래 가는 지식" 으로 설계해 놓고

**보완**

- **2안** 명세를 코드에 맞추고, 접기 규칙을 종류별로 나눈다 — `howto` 는 "앞 5줄" 이 아니라 "번호 목록의 제목 줄만" 남긴다.
- 1안이 싸고 뜻도 맞다.

## 8. `updated_at` 이 파일 mtime 이다 — 중

**무엇** 색인의 `updated_at` 은 파일 수정 시각이고, `mem list`(= 훅 주입의 모든 절)는 `ORDER BY updated_at DESC` 다.

**근거**
- `internal/index/indexer.go:205` `insertMemory(..., file.ModTime.Unix(), ...)`
- `internal/search/engine.go:116` `" ORDER BY updated_at DESC LIMIT ?"`
- `internal/lint/fix.go:78` `fixUpdatedAt` 은 아예 "파일 mtime 으로 맞추기" 를 고침 항목으로 둔다

**왜 문제인가** `store/` 는 git 추적물이다. **다른 기계에서 clone 하면 모든 파일의 mtime 이 checkout 시각으로 같아진다.**
그러면 "최근 결정 5건" 이 사실상 무작위 5건이 된다 — 새 기계에서 처음 세션을 여는 순간, 즉 이 도구가
가장 값어치를 내야 할 자리에서 품질이 떨어진다. `lint` 의 `stale`(`updated_at` 180일 경과) 검사도 같이 무의미해진다.
git 이 mtime 을 보존하지 않는다는 건 확실하지만, clone 상황을 실제로 재현해 보지는 못했다.

**보완**
- **1안 (추천)** 순서 기준을 `updated_at` 이 아니라 **`date`(머리말) → `created_at`** 으로 바꾼다.
  `date` 는 파일 안에 있으니 clone 을 타지 않는다. `updated_at` 은 증분 색인 판정에만 쓴다.
- **2안** 머리말에 `updated: YYYY-MM-DD` 칸을 새로 두고 `patch`·`amend`·gc 가 적는다. 정확하지만 칸이 는다.
- 어느 쪽이든 `stale` 검사는 `date` 기준으로 바꿔야 한다.

**무엇** `## 관련` 절은 `--query` 가 있을 때만 채워지는데, **훅 경로에는 query 를 넣을 자리가 없다.**

**왜 문제인가** 주입되는 27건은 **저장소 전체의 최신·고정** 이지 이번 세션이 할 일과 아무 상관이 없다.
지금처럼 저장소가 한 툴 얘기(193/205 가 `scope: aimemorytool`)면 우연히 맞지만,
설계 전제인 "툴킷 = 여러 툴이 한 저장소" 가 되면 **주입의 대부분이 지금 안 만지는 툴 얘기**가 된다.

**보완**
- **1안 (추천)** 훅이 **git 상태에서 질의를 만든다** — 현재 브랜치 이름, 최근 커밋 제목, 또는 `cwd` 의 폴더 이름.

- **2안** `scope` 를 폴더로 잇는다 — `cwd` 가 `AIMemoryTool/` 아래면 `scope` 가 그 이름인 것을 먼저 넣는다.

- **3안** `UserPromptSubmit` 훅을 하나 더 두고 첫 프롬프트로 `mem search` 를 돌린다.
  설계가 훅 1개를 고집한 이유(시작 비용)는 세션당 1회에 관한 것이라, 매 프롬프트 훅은 다른 비용 계산이 필요하다 — 지금은 권하지 않는다.
- 1안이 값싸고 효과가 크다. 최소한 **"주입은 세션 내용을 모른다"** 를 설계 한계로 적어야 한다.

## 10. `mem.toml` 이 한 번 쓰이면 못 따라간다 — 중

**무엇** 확정된 gc 값과 이 저장소의 실제 설정이 다르다.

**근거**
- 결정 `20260822-850b524e` : "차가움 임계 4,000 → **20,000**", 아카이브 1GB
- `internal/config/config.go:70` `Default(...)` : `ColdCount: 20000` ✔

**왜 문제인가** `mem.toml` 은 `mem init` 이 한 번 쓰고 그 뒤로 아무도 안 고친다.
기본값을 바꾼 결정이 **이미 깔린 저장소에는 영영 안 닿는다.** 그리고 이 어긋남을 잡는 검사가 없다 —

  "기본값이 바뀌었다 : cold_count 4000 → 20000. 일부러 바꾼 것이면 무시해도 된다" 고 한 줄. `secret-stale` 과 같은 모양이다.
- **2안** `mem init` 을 다시 돌리면 **없는 칸만 채우고 옛 기본값이면 새 기본값으로 올린다**(사람이 바꾼 값은 그대로).
  구분이 어려우므로 1안이 안전하다.
- 이와 별개로 `mem.toml` 은 왜 `schema` 판을 갖고 있으면서 자기 자신의 이주는 안 하는지 명세에 설명이 없다. 그 절을 채우는 게 좋다.

## 11. 저장소를 한 번에 하나만 연다 + `scope` 한 칸이 export 단위 — 중

**무엇** 두 문제가 같은 뿌리다 — "기억이 어디에 속하나" 를 표현하는 칸이 `scope` **문자열 하나**뿐이고,
열리는 저장소는 **프로젝트 1 + 전역 1** 로 고정이다.

**근거**
- `internal/config/locate.go:33-56` `Find` — 위로 올라가다 `Memory/mem.toml` 을 처음 만나면 멈추고, `.git` 에서도 멈춘다
- `internal/config/locate.go:79` `Resolve` — 돌려주는 것은 project 하나 + global 하나
- `internal/export/export.go:99` `pick` — `contains(scopes, found.Memory.Scope)` **정확히 일치**만
- 실측 scope 분포 : `aimemorytool 193 · officina 7 · mem 2 · mem-search 1 · claude-code 1 · aimemorytool-lint 1`

**왜 문제인가**
- **툴을 떼어 낼 때** : `mem export --scope aimemorytool` 로는 `mem`·`mem-search`·`aimemorytool-lint` 5건이 남는다.
  전부 그 툴 얘기인데 이름이 다르다는 이유로 안 따라간다. 사람이 scope 목록을 손으로 훑어야 한다는 뜻이다.
- **떼어 낸 뒤** : AIMemoryTool 이 자기 `.git` 을 갖는 순간, 그 폴더 안에서 돌린 `mem` 은 `.git` 에서 멈춰
  바깥 `<작업폴더>/Memory` 를 **못 본다**(그게 설계 의도다). 그러면 남겨 둔 기억은 그 폴더 안에서 영영 안 보인다.
  거꾸로 스튜디오 저장소 뿌리에서 세션을 열면 **서브모듈 안 툴의 기억이 안 보인다.** 어느 쪽에서 일하든 절반만 보인다.
- **모노레포에서 여러 툴을 동시에 만질 때** 도 같다. 저장소는 하나만 열린다.

**보완**
- **1안 (추천)** `scope` 를 **접두 계층**으로 규정한다 — `aimemorytool` / `aimemorytool-lint` / `aimemorytool-search`.
  `export --scope aimemorytool` 은 `aimemorytool*` 를 다 가져가고, 검색 필터도 접두 일치로 본다.
  칸을 안 늘리고 규칙만 더하는 값싼 길이다. `기억파일규격.md` 2절에 한 줄 더하면 된다.
- **2안** `scope` 를 배열로 만든다(기억 하나가 프로젝트와 툴에 동시에 속함). 표현력은 제일 좋지만 색인·필터·lint 를 다 손봐야 한다.
- 여러 저장소는 **3안 : `mem.toml` 에 `extra_repos = ["AIMemoryTool/Memory"]` 를 두고 읽기 전용으로 같이 연다.**
  이미 전역 저장소를 읽기 전용으로 같이 여는 기계장치가 있으므로 그 자리에 목록을 끼우면 된다.
- 지금 당장은 **떼어 내기 절차(README 또는 `mem help export`)에 "scope 목록을 `mem list --json` 으로 훑어 빠진 것을 확인하라"**
  한 줄이라도 넣는 게 좋다.

**보완**
- 주입할 게 없을 때 **한 줄짜리 최소 블록**을 낸다 — `> mem : 기억을 못 읽었다 (mem version 으로 확인)`.
  한 줄이면 예산에도 안 걸리고 불변조건 3(세션을 막지 않는다)도 안 깨진다.
- 또는 `mem version`·`mem search` 등 사람이 부르는 명령이 이 상태를 눈에 띄게 알린다(이미 종료 코드 2 는 낸다).
- **주의** : 이 한 줄도 "자료" 구분선 바깥에 두면 지시로 읽힌다. 자료 구역 안에 넣는다.

## 15. 빠진 불변조건 — 원본 불변성·시계·id 날짜 — 하

**무엇** 불변조건 6개는 "누가 쓰나 · 훅은 조용하다 · 경로 감옥 · 주입 살균 · 색인 검증" 을 덮지만,
**원본 자체의 성질**을 지키는 조건이 없다.

**근거·상황**
- **id 날짜와 `date` 가 갈릴 수 있다** — `id` 는 승격 시각(`internal/index/promote.go:129` `model.NewID(request.Body, r.now)`),
  `date` 는 add 시각(`request.Date`). 자정을 넘겨 색인되면 파일은 `store/2026/08/20260823-xxxx.md` 인데 `date: 2026-08-22` 다.
  `StorePath` 는 id 를 보므로 깨지진 않지만, 검색 결과의 날짜와 id 가 어긋나 사람이 헷갈린다.
- **시계 역행** — 기계 시각이 뒤로 가면 `created_at` 이 뒤섞이고 gc 나이 계산·감쇠가 흔들린다. 대비가 없다.
- **원본 불변성** — "한 번 색인된 `store/` 파일의 id·date·본문은 gc·amend 이외에는 안 바뀐다" 는 조건이 없다.
  실제로 합치기(발견 12)와 `lint --fix`(발견 3)가 이 자리를 비집고 들어와 있다.

**보완**
- 불변조건에 한 줄 더한다 : **"한번 승격된 기억의 `id`·`date`·본문은 gc(접기)와 명시적 amend 말고는 안 바뀐다."**
  이 한 줄이 있었으면 발견 3·12 가 설계 단계에서 걸렸을 것이다.
- id 는 **`request.Date` 를 앞자리로** 쓰게 바꾼다(발견 4 의 1안을 하면 자연히 해결된다).
- 시계는 `created_at` 이 미래면 lint 경고 한 줄이면 충분하다.
