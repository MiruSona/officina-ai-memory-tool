# 재순위 모델(cross-encoder) 실험 — 2026-10-05

> 다국어 cross-encoder 재순위 모델을 `mem` 검색 뒤에 붙이면 얼마나 좋아지고 얼마나 느려지나 잰다.
> 저장소 코드는 안 고쳤다. 모두 스크래치 복사본(`scratchpad\memrerank\`)에서 쟀다.
> 앞 문서 : `2026-10-05-abstain탐침과칸조사.md`(탐침 셋·기준값) · `2026-10-05-재순위손잡이실험.md`(표 모양).

## 0. 결론 먼저

- **「답 있음」 문턱(게이트)은 또 실패했다.** 세 모델 · 네 글 모양 · K 네 개 어디서도 기준을 다 넘는 문턱이 없다.
  탐침 오답을 반으로 줄이는 문턱(τ ≥ 0.05 언저리)에서는 **반드시 답 있는 질문도 같이 버린다**(G2 오배제 증가 또는 206 v2 하락).
  코사인 문턱이 실패했던 것과 같은 모양이다. → **게이트 안은 기각.**
- **순서만 바꾸는 안(섞음 blend)은 기준을 넘는 판이 있다.** 815 v3 r@5 53 → 55~56, 206 v2 그대로, G2 그대로, 새로 밀린 답 0~1.
  하지만 **+2 중 +1 은 후보를 넓힌 덕**(재순위 없이 K20 으로 넓히기만 해도 54)이고, 판을 69건에 대고 여러 손잡이를 골랐으므로 **잡음 안쪽일 수 있다.**
- **지연은 「한 프로세스 안에서」는 900ms 안**이지만, **CLI 한 번 = 프로세스 하나**라 모델 읽기 1.2~2.1초가 매번 붙는다.
  지금 모양 그대로 붙이면 p95 900ms 를 못 맞춘다. 토크나이저 굽기(결정 10 과 같은 처리)·상주 프로세스가 있어야 한다.
- **Go 쪽은 bge-reranker-v2-m3(Unigram)만 지금 길로 읽을 수 있다.** 가장 좋았던 Horizon-Labs 두 모델은 BPE 토크나이저라 Go 로더를 새로 짜야 한다.

### 사용자가 정할 것

1. **순서만 바꾸는 재순위를 「선택 설치」로 더 밀어 볼까.** 밀면 다음 일은 ⓐ 토크나이저를 굽거나 Go 로 읽어 모델 읽기 시간을 줄이기, ⓑ 다른 셋(새 골든셋)에서 +2 가 남는지 다시 재기. 안 밀면 이 실험으로 닫는다.
2. **게이트(답 없음 판정)는 모델로도 안 된다 → 접을까.** 코사인·cross-encoder 둘 다 같은 모양으로 실패했다. 남는 길은 탐침 질문 쪽(칸 설계)뿐이다.
3. **한국어 미세조정판 `dragonkue/bge-reranker-v2-m3-ko`(Apache-2.0) 를 잴까.** safetensors 2.27GB 뿐이라 이번 승인(1GB 이하)을 넘고 ONNX 변환도 필요하다. 원판 bge-m3 가 가장 약했으므로 기대는 크지 않다.

## 1. 무엇을 쟀나

| 안 | 내용 |
| --- | --- |
| 1. 순위 | strict 상위 K(10·20·30·50)를 재순위 점수로 덮어쓰기 · 구조 점수와 섞기(w 0.3/0.5/0.7) · 느슨 후보까지 포함 |
| 2. 게이트 | strict 상위 10 의 재순위 최고점이 τ 아래면 다 버림(abstain) · 건마다 τ 아래 답만 내림 |
| 3. 1+2 | 섞은 차례 위에 게이트 |
| 4. 모델 셋 | Horizon-Labs small(141M) · base(308M) · bge-reranker-v2-m3 |

- **섞음** : 점수 = w·sigmoid(CE) + (1−w)·minmax(strict 후보의 구조 점수). strict 후보만 다시 줄 세우고 느슨 후보는 원래 차례로 뒤에 붙인다. 칸(strict 판정)은 안 바꾼다.
- **K10** : 지금 화면 10건만 다시 줄 세움. K20 이상은 `limit K` 로 검색해 후보를 넓힌 뒤 줄 세우고 상위 10 을 화면으로 쓴다.
- **글 모양** : T = 제목 · TS = 제목+요약 · TSB100 / TSB300 = 제목+요약+본문 앞 100 / 300자. 최대 길이 384 토큰(bge 512), 문서 쪽만 자른다.
- **게이트 문턱 고르기** : J = v3 r@5 적중 + v3 맞은 abstain + 탐침 맞은 abstain 이 최대인 τ 를 격자(0~0.9, 18칸)에서 고른다.
  815 에서 짝수 줄로 고르고 홀수 줄에서 재고 거꾸로도 한다(두 겹 교차). 206 은 815 전체로 고른 τ 를 그대로 얹어서만 잰다. **맞춘 자료로 채점하지 않았다.**

### 셈이 `mem eval` 과 같은지

캐시한 검색 결과로 바깥에서 지표를 다시 셌다. 재순위 없는 기준을 `mem eval` 결과와 12조합(모드 2 × 저장소 2 × 셋 3) 건마다 맞춰 봤다.
11조합은 건마다 같다. 1조합(낱말 모드 · 206 · v2 · K20 덤프)은 점수가 같은 두 건(0.18276)의 차례만 바뀌었고 순위·지표는 같다.

재순위가 없을 때 값이 그대로인 것은 이 실험의 기준 줄이 `mem eval` 과 같은 것으로 확인했다.

- **INT8 더 줄이기도 해 봤다.** hl-small 에 MatMul 동적 INT8 양자화(141.5MB)를 걸었더니 약 25% 빨라졌지만 점수가 크게 바뀌었다(sigmoid 차 평균 0.218, 최대 0.98). 기각.

## 8. 절차 · 명령

스크래치 폴더 `scratchpad\memrerank\` (경로가 길어 `subst R:` 로 줄여 썼다).

1. `src\` = `git archive 1ba1b33` 로 뽑은 AIMemoryTool 복사본 + 숨은 명령 `cmd\mem\cmd_rrdump.go` 하나 추가.
   `rrdump --golden <셋> --repo <저장소> --k <K>` 는 `mem eval` 과 같은 검색 옵션으로 limit 10 과 limit K 를 둘 다 돌리고, 원시 strict 검색(밀림 판정용)까지 건마다 JSON 으로 낸다.
   `CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o mem-rr.exe ./cmd/mem`
2. `dump.sh <home|home2> <repo3|repo206>` — 기준 exe 로 `mem eval` 을, `mem-rr.exe rrdump` 로 K50·K30·K20 덤프를 셋 셋(abstain-probe · goldenset-v3 · goldenset-v2)에 대해 뽑는다.
   HOME 은 의미 모드(e5-small-ko-v2) 와 낱말 모드 둘. `MEM_INSTALL_NO_PATH=1`, USERPROFILE/HOME 을 스크래치로 돌린다.
3. 가상환경 `memrerank\venv`(Python 3.14) — onnxruntime 1.30.0 · tokenizers 0.23.2 · numpy 2.5.3 · pyyaml · onnx 1.23.1. 전역 pip 안 씀.
4. `verify.py` — 바깥 셈과 `mem eval` 을 건마다 대조(§1).
5. `fill.py <모델> <글 모양들>` — 후보·화면 쌍 8272개 점수를 캐시(`logs\ce-<모델>-<글>.json`). 걸린 시간 : hl-small T 92s · TS 162s · TSB100 276s · TSB300 662s · hl-base TS 322s · bge-m3 TS 480s.
6. `exp.py` · `exp2.py <모델> <글> [home|home2] [문턱 고른 곳]` — 판 표·게이트·두 겹 교차·건별 차이. `curve.py` — 문턱 곡선. `final.py` — §2·§4 표.
7. `bench.py <모델> <글> <스레드>` — §5 지연.
