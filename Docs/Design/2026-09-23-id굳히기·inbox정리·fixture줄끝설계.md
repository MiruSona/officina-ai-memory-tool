## 1. 결론

| # | 문제 | 정한 것 |
| --- | --- | --- |
| 1 | `add` 가 찍은 id 가 `index` 전엔 안 보이고, 승격 때 바뀔 수도 있다 | **`add` 가 자기 큐 파일만 그 자리에서 승격한다.** 락을 못 잡으면 지금처럼 큐에 두고 지금 안내를 찍는다 |

| 5 | add 가 벡터도 채우나 | **안 채운다.** 모델을 올리는 값이 크다. 다음 `index` 가 채우고 그 사이엔 의미 검색에서만 빠진다 — 구현하며 정함 |

| 7 | 훅 알림의 bad 종류별 건수 | **건수만 둔다.** 쪼개면 훅이 bad 파일을 열어야 한다. 종류는 `mem index --bad` 가 보여준다 — 구현하며 정함 |

| 9 | add 즉시 승격의 벽시계 | **작은 저장소에서 add 한 번 80~92ms** (5건 저장소, 2026-09-26). 1초에 한참 못 미쳐 `--queue-only` 는 안 만든다. 20k 저장소 실측은 아직이다(5절) |
| 10 | 기다리는 사이 남이 먼저 승격 | **`index.db` 영수증 표 `promoted`(큐 파일 → 실제 id, 10분)** 를 모든 승격 길이 남기고, 락을 잡은 add 가 제 파일이 없으면 거기서 읽는다. 없으면 「이미 승격됨」 으로 stdout 을 비운다 — 틀린 id 를 찍지 않으려고 (리뷰 2026-09-26) |
| 11 | 색인을 새로 세울 판의 add | **승격도 색인도 안 하고 큐에 둔다.** 빈 색인에 대고 승격하면 쌍둥이를 못 봐 겹친 파일이 생긴다. 리뷰 안(「승격만 하고 색인은 미룬다」)보다 한 걸음 더 물렀다 (리뷰 2026-09-26) |

3번에서 새로 알아낸 것이 있다. **`testdata/lint/crlf.md` 는 커밋 안에서 이미 LF 다** (`git show HEAD:…` 로 확인).
autocrlf 가 커밋할 때 CRLF 를 LF 로 바꿔 넣었다. 그래서 `.gitattributes` 만 달면 오히려 **리눅스에서 깨진다**
(CRLF 파일이 하나도 없어 고친 것이 1건). 지금 Windows 에서 「CRLF 시험」이 돌아가는 것도 체크아웃이 모든 fixture 를
CRLF 로 바꿔 준 덕이다 — 그래서 3건을 고쳐 `2건이어야 한다` 에 걸린다.

## 2. 색인 전 id 굳히기

### 2-1. 지금 무엇이 id 를 바꾸나

`add` 는 `model.QueueID(큐이름, 본문, 날짜)` 를 찍는다. 승격(`internal/index/promote.go applyAdd`)에서 이 id 가 안 남는 길은 넷이다.

| 길 | 어디서 | add 관문(`quality.Gate`)이 이미 보나 |
| --- | --- | --- |
| 비밀정보 → `bad` | `scanSecret` | **본다** (`secret-pattern` 거절). 큐에 직접 쓴 파일만 여기 걸린다 |
| 규격 위반 → `bad` | `createNew` 의 `ValidateWith` | 거의 본다. 관문과 승격 사이에 `vocab.toml` 이 바뀌면 걸린다 |
| 완전중복 → 쌍둥이 id | `db.sameBody` · `sameBodyHere` | **안 본다** (DB 가 필요하다) |
| 근사중복 → 닮은 기억 뒤에 붙음 | `findTwin`(7일 · 자카드 0.8) → `appendTo` | **안 본다** (관문의 중복 관문은 경고·거절용, 합침은 승격 몫) |
| id 충돌 → 소금 친 id | `freeID` | 안 본다 (32비트 해시, 드묾) |

`--hold` 와 `--by` 는 합침을 건너뛰고(09-23) 완전중복만 본다. 즉 **id 를 바꾸는 것은 DB 를 봐야 아는 판정뿐이다.**
그 판정은 락을 쥔 승격만 할 수 있다.

### 2-2. 선택지

| | A. add 때 `index` 통째 | B. `show` 가 inbox 도 본다 | **C. add 가 자기 것만 승격** |
| --- | --- | --- | --- |
| 찍힌 id 가 참인가 | 참 | **아니다** (합쳐지면 바뀐다) | 참 |
| 바로 `show`·검색 | 된다 | `show` 만 (검색은 안 됨) | 된다 (벡터 검색은 다음 `index` 뒤) |
| md 파일이 곧 생기나 (커밋에 들어가나) | 생긴다 | 안 생긴다 | 생긴다 |
| 남의 큐까지 건드리나 | **건드린다** (남의 add 승격 · gc 조건 · 벡터 · 이웃 링크) | 아니다 | 아니다 |
| 걸리는 시간 | 증분 10건 530ms + 벡터 | 0 | 한 건 승격 + 증분 색인 (A 보다 짧다) |
| 락을 못 잡으면 | 조용히 건너뜀 → 여전히 안 굳음 | 상관없음 | 짧게 기다리고, 그래도 없으면 큐로 (지금과 같음) |
| `--by` 가 다른 회차로 갈리는 한계(09-23) | 준다 | 그대로 | **없앤다** (add 와 덮임 표시를 한 락 안에서 같이 먹는다) |

B 는 이미 반쯤 있다 — `show` 가 「아직 색인 전이다」 를 찍는다(`cmd_show.go queuedNote`). 불편의 뿌리(「id 가 바뀔 수 있다」)는 못 푼다.
A 는 add 한 번이 남의 일(gc 조건·벡터)까지 끌고 와 느리고 예측이 어렵다. **C 로 정한다. B 는 C 의 뒷길로 남긴다.**

### 2-3. 정한 동작

```text
mem add …
  ① 관문 (지금 그대로)
  ② inbox/new 에 add 파일 쓰기 (+ --by 면 patch 파일) — 지금 그대로
  ③ 락 잡기 : TryLock 을 50ms 간격으로 최대 1초
       못 잡음 → 지금처럼 큐 id 를 찍고 「색인 대기」 안내. 끝
  ④ 잡음 → ②에서 쓴 파일만 차례대로 promoteOne (지금 코드 그대로)
  ⑤ 증분 색인 (indexChanged) — gc·벡터·이웃 링크는 안 한다
  ⑥ 락 풀기 → 결과를 찍는다
```

| 승격 결과 | stdout (한 줄) | stderr 끝줄 | 종료 |
| --- | --- | --- | --- |
| 새 파일 | 새 id | `저장됨 : <id>` | 0 |
| 완전중복 | **쌍둥이 id** | `저장됨 : <id> — 같은 본문이 이미 있어 그 기억을 가리킨다` | 0 |
| 닮은 기억 뒤에 붙음 | **닮은 기억 id** | `저장됨 : <id> — 닮은 기억 뒤에 한 절로 붙였다` | 0 |
| bad (규격·비밀정보) | 없음 | `저장 안 됨 — <까닭>. inbox/bad 에 뒀다 (mem index --bad)` | 2 · 4 |
| 락 못 잡음 | 큐 id | 지금 문구 `AddQueuedNote` 그대로 | 0 |

- **stdout 은 늘 id 한 줄**이라는 약속은 지킨다. 스크립트가 받는 값이 이제 **실제로 남은 id** 다.
- `--jsonl` 도 같다. 락은 묶음 전체에 한 번 잡고, 줄 차례대로 승격한다.
- `--check` 는 아무것도 안 쓴다 (지금 그대로).
- 승격 결과를 받으려면 `runner` 가 이름별 결과(`상태 · 최종 id · 까닭`)를 적어 둬야 한다.
  `applyAdd` 의 네 갈래(중복 · 붙임 · 새 파일 · 오류)에서 한 줄씩 적는다.

## 3. inbox/bad 정리

### 3-1. 무엇이 쌓이나

| 들어오는 것 | 언제 | 푸는 길 |
| --- | --- | --- |
| add — 비밀정보 | 큐에 손으로 쓴 파일 | 값을 빼고 다시 `mem add` |
| add — 규격 위반 | 관문 뒤 표가 바뀜 · 옛 규격 큐 | 고쳐서 다시 `mem add` |
| patch · body — 대상 없음·칸 틀림 | 덮은 옛 id 가 없어짐 (09-20 타일 5번) | 할 것 없다. 치운다 |
| JSON 깨짐 · 모르는 op | 손으로 쓴 파일 | 할 것 없다. 치운다 |

까닭은 이미 `local/bad-reasons/<이름>.err` 에 한 줄 남는다 (중화됨). **지우는 명령도 이미 있다** — `mem index --clear-bad`.
빠진 것은 ① 지우지 않고 보기만 하는 길 ② 훅 알림이 엉뚱한 명령(`mem index`)을 권하는 것 둘이다.

### 3-2. 선택지

| | 새 명령 `mem inbox --bad`·`--purge` | **`mem index --bad` 더하기** | 오래된 것 자동 삭제 |
| --- | --- | --- | --- |
| 명령 수 | 17 → 18 (도움말·권한 목록·문서 다 늘어남) | 그대로 | 그대로 |
| 이미 있는 `--clear-bad` 와 | 겹친다 | 짝이 맞는다 (보기 / 치우기) | — |
| I5 자동 삭제 없음 | 지킨다 | 지킨다 | **어긴다** |

**가운데로 정한다.**

### 3-3. 명령 꼴

```text
mem index --bad          보기만 한다. 아무것도 안 바꾼다. 락도 안 잡는다
  inbox/bad 2건
  - 1758…json · add   · 규격 위반 : tags … · 고쳐서 다시 mem add
  - 1759…json · patch · 대상 기억 없음 : 20260920-… · 치워도 된다
  치우려면 : mem index --clear-bad
mem index --clear-bad    지금 그대로 (보여주고 지운다, 사람이 친다)
```

- 종류(add/patch/body/깨짐)는 파일의 `op` 를 읽어 가른다. `.err` 꼴은 안 바꾼다 — 옛 파일도 그대로 읽힌다.
- 줄은 전부 `internal/safe` 를 지난다 (I3). 본문·값은 안 찍는다.
- 치울 때 `local/received/` 에 옮겨 두지는 **않는다** — 비밀정보로 걸린 것이 git 밖이라도 디스크에 한 벌 더 남는다.
- **bad 를 다시 큐로 되돌리는 명령은 안 만든다.** 되돌려도 같은 까닭으로 또 걸린다. 고쳐서 다시 `add` 가 맞다.
- 2장의 add 즉시 승격에서 난 bad 도 같은 자리·같은 까닭 파일을 쓴다 — 두 길이 한 곳에 모인다.

### 3-4. 훅 알림

| | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 문구 | `inbox/bad 에 N건이 실패해 있다. mem index 를 한 번 돌려라` | `inbox/bad 에 N건 — mem index --bad 로 까닭을 보고 --clear-bad 로 치운다` |
| 파일 이름·까닭 | 없음 | **넣지 않는다.** 알림은 2줄 고정이고 훅은 짧아야 한다. 자세한 것은 명령 몫 |

피드백(09-20 찹쌀이)은 「이름과 까닭을 훅에 찍어 달라」였다. **명령을 가리키는 쪽으로 푼다** — 훅에 싣는 글이 늘수록 주입 면이 넓어진다.

### 3-5. 고칠 파일 · 시험

| 파일 | 무엇 |
| --- | --- |
| `cmd/mem/cmd_index.go` | `--bad` 옵션 · `showBad()` |
| `internal/store/inbox.go` | `BadOp(name)` — bad 파일의 `op` 만 읽는다 (깨졌으면 「깨짐」) |
| `internal/i18n/hook.go` · `i18n.go` | `HookNoticeBad` 문구 · 보기 화면 문구 · 종류별 푸는 길 |
| `Docs/Guide/명령명세.md` · `동시성과안전.md` 2절 · `훅연동.md` | 옵션·문구 |

시험 : `--bad` 뒤 파일 수·내용이 그대로다 · 종류 넷이 제 푸는 길을 찍는다 · 까닭 파일 없는 옛 항목도 찍힌다 ·
훅 알림에 `--bad` 가 들어 있다 · 알림 줄에 파일 이름이 없다.

| `git ls-files --eol testdata` | 173개 모두 `i/lf w/crlf` |
| `crlf.md` 커밋 안 바이트 | **LF** — CRLF fixture 가 커밋 때 사라졌다 |
| `bom.md` | BOM 은 커밋 안에 남아 있다 |
| 실패 모양 | 고친 것 3건 (22222222 · ffff5555 · ffff6666) — `field.md` 도 체크아웃이 CRLF 로 만들어 걸렸다 |
| 같은 fixture 를 쓰는 시험 | `TestFixOnlyReversible` · `TestFixWithoutLockOnlyChecks` · `TestFixReadOnlyStore` |

`TestFixWithoutLockOnlyChecks` 는 「파일에 `\r\n` 이 남아 있다」를 본다. **리눅스에서는 이 시험도 깨진다** — 지금 통과는 Windows 체크아웃 덕이다.

### 4-2. 선택지

| | `testdata/** -text` + CRLF 로 다시 커밋 | **`text eol=lf` + 시험이 CRLF 를 만든다** | 시험이 fixture 를 늘 LF 로 고쳐 읽는다 |
| --- | --- | --- | --- |
| fixture 바이트가 기계마다 같나 | 같다 | 같다 (LF) | 디스크는 다르다 |
| 편집기가 저장하며 줄끝을 바꾸면 | **다시 깨진다** | 커밋 때 LF 로 돌아온다 | 안 깨진다 |
| 시험이 무엇을 재는지 읽히나 | 파일을 열어 봐야 안다 (눈에 안 보이는 `\r`) | 코드에 `\r\n` 이 보인다 | 보인다 |
| 이미 lintOnlyCases 가 쓰는 꼴과 | 다르다 | **같다** (`RuleCRLF` 줄이 이미 코드로 CRLF 를 만든다) | — |

**가운데로 정한다.** 셋째 것은 fixture 를 LF 로 고정하면 필요 없다 — 한 겹으로 충분하다.

### 4-3. 정한 것

`AIMemoryTool/.gitattributes` (새 파일) :

```text
# 시험 자료는 어느 OS 에서 받아도 LF 다. CRLF·BOM 시험은 시험 코드가 바이트를 만든다.
testdata/** text eol=lf
# 한글 cp949 바이트 — 줄끝 변환이 끼면 안 된다
testdata/lint/encoding.cp949 -text
```

- **`text=auto` 는 안 쓴다** — mem `20260918-cb031d0f` 의 함정 그대로다. `text` 로 못박는다.
- 범위는 `testdata/**` 만. `*.go` 까지 넓히는 것은 5장.
- 시험 : `copyFixture` 옆에 `copyFixtureCRLF(t, opened, "crlf.md")` 를 두고 읽은 바이트의 `\n` 을 `\r\n` 으로 바꿔 쓴다.
  CRLF 가 필요한 세 시험이 이것을 쓴다. `crlf.md` 파일 이름은 그대로 둔다 (「CRLF 로 만들어 쓰는 원본」이라고 머리 주석 한 줄).
- **받은 사본 정리** : `.gitattributes` 를 넣은 뒤 이미 받은 Windows 사본은 파일이 CRLF 인 채로 남는다.
  `testdata` 를 지우고 `git checkout -- testdata` 로 다시 받는다 (커밋 안 내용은 이미 LF 라 `--renormalize` 할 것이 없다).

### 4-4. 시험

- Windows(autocrlf=true)에서 새로 받은 사본 : `go test ./...` 전부 통과. `git ls-files --eol testdata` 가 `w/lf attr/text eol=lf`.
- `encoding.cp949` 는 `-text` 로 바이트가 그대로 (`lintOnlyCases` 의 `RuleEncoding` 이 통과).
- 리눅스(또는 `core.autocrlf=false` 사본)에서도 같은 결과 — 확인 기계가 없으면 `autocrlf=false` 로 새로 받은 사본으로 대신한다.
