# 무효화 전파 설계 — `mem set --by` 가 근거 삼은 기억을 검토 큐로

- 대상 : `AIMemoryTool/` (mem)
- 근거 조사 : `../Research/2026-08-30-기억이아니라상태관리-Lemmalog조사.md` 3절 1번·4번
- 쓴 날 : 2026-08-30

---

## 1. 결론

**파일에 새로 쓰는 것은 하나도 없다.** `mem set X --by Y` 는 지금 하는 일(X 의 `superseded_by`·`invalid_at` 채우기)을 그대로 하고, **X 를 근거로 삼은 기억이 몇 건인지 화면에 한 줄 알려 주기만** 한다. 그 기억들을 사람에게 보이는 자리는 `mem review --kind basis` 라는 새 갈래이고, 이 큐는 **매번 새로 계산한다.**

그래도 되는 까닭이 코드에 있다. `internal/review/review.go:423 loadMemories` 는 저장소의 md 를 **전부 읽어** `quality.CheckRepo` 에 넘긴다. 검토 큐는 색인(SQLite)을 한 줄도 안 본다. 그러니 「X 가 죽었나」(X 의 md)와 「Y 가 X 를 근거로 삼았나」(Y 의 md)는 둘 다 이미 손에 있고, **상태를 md 에 적어 둘 이유가 없다.** 새 머리말 칸 0개, 마이그레이션 0건.

색인은 딱 한 자리에만 쓴다 — `mem show X` 의 「나를 근거로 삼은 기억」 절. 여기는 저장소 전체를 읽으면 안 되는 자리라 역참조 질의가 필요하다.

## 2. 정의 — 「X 를 근거로 삼은 기억」

### 무엇을 넣나

| 관계 | 넣나 | 왜 |
| --- | --- | --- |
| `Y.sources` 에 `mem:X` 가 있다 | **넣는다 (근거)** | 이게 진짜 근거다. `decision`·`issue`·`caution`·`fact` 는 `sources` 가 필수라 이 관계가 가장 믿을 만하다 |
| `Y.links` 에 `X` 가 있다 | **넣는다 (링크)** | 조사 3절 1번이 `--link` 도 셌다. 다만 links 는 「이어지는 기억」이라 근거보다 약하니 **큐 문구를 「링크」로 갈라 적는다** |
| `Y.superseded_by == X` | **뺀다** | Y 는 X 에게 이미 덮여 죽었다. 죽은 기억을 「낡았을지 모른다」고 다시 부르는 것은 뜻이 없다 |
| `Y.id == X` (자기참조) | **뺀다** | 자기가 자기 근거인 기억은 판정할 것이 없다 |
| Y 가 이미 무효 (`invalid_at` 이 지났거나 `superseded_by` 가 있다) | **뺀다** | 검색·훅에서 이미 빠진 기억이다. 사람 화면을 채울 값이 없다 |
| `auto_links` | **뺀다** | 기계가 만든 파생 표다. 사람이 적은 `links` 만 본다 (`cmd_set.go:297` 주석과 같은 원칙) |

**X 가 죽었다**의 뜻 : `X.superseded_by` 가 있거나 `X.invalid_at` 이 오늘까지 지났다. 둘 중 하나면 된다 — 덮은 새 기억 없이 그냥 무효가 된 것도 근거가 죽은 것이다.

### 전파 깊이 — **1단만**

X 를 직접 가리킨 Y 까지만 본다. Y 를 가리킨 Z 는 **안 본다.** 까닭 셋 :

1. **판정은 사람이다.** X 가 죽었다고 Y 가 틀린 것은 아니다. 「틀렸을지 모르는 Y」에 기댄 Z 까지 부르면 근거가 두 겹 약해져 큐가 잡소리로 찬다.
2. **연쇄는 사람 손으로 저절로 굴러간다.** 사람이 Y 를 보고 `mem set Y --by …` 로 덮으면, 그 순간 Z 가 **1단 대상이 된다.** 한 칸씩, 사람 판정을 거쳐 굴러간다. 이게 우리 원칙에 맞는 연쇄다.
3. **순환에서 안 터진다.** `links` 는 서로 가리킬 수 있어 깊이 제한 없이 돌면 무한 루프 방어 코드가 따로 필요하다. 1단은 그럴 일이 없다.

## 3. `mem set X --by Y` 때 무엇이 일어나나

### 지금과 같은 것

`addSupersede`(`cmd_set.go:182`)가 `superseded_by`·`invalid_at` 을 채우고 `WritePatch` 로 큐에 넣는다. **여기는 한 글자도 안 고친다.**

### 더하는 것 — 화면 한 줄뿐

`queueSet` 의 `SetSuperseded` 줄 바로 뒤에 붙인다.

```
덮음 표시를 달았다 : 20260822-aaaa 를 20260830-bbbb 가 덮는다.
이 기억을 근거로 삼은 기억이 3건 있다 : 20260828-1111 20260829-2222 20260830-3333
→ mem review --kind basis   (사람이 하나씩 판정한다)
```

- 0건이면 이 두 줄을 **안 찍는다.**
- 색인이 없거나 못 열면 `이 기억을 근거로 삼은 기억은 못 셌다 (색인이 없다 — mem index 뒤에 mem review --kind basis)` 한 줄. **0건이라고 말하지 않는다.**
- 색인은 `showPath`(`cmd_show.go:142`)와 같은 꼴로 연다. 프로세스당 열기 2회 상한(설계 7-4a) 안이다.
- `--by-new` 는 덮은 새 기억이 없어 X 가 아직 안 죽었다 → **아무것도 안 찍는다.** `mem add … --by X`(`cmd_add.go:167`)도 같은 줄을 찍는다.

### 큐에 「올리는」 일은 없다

**review 는 매번 계산한다.** `mem set` 이 어디에도 표시를 안 남겨도 다음 `mem review` 가 저장소를 훑어 같은 답을 낸다. 색인을 지워도, `.db` 를 통째로 버려도 큐는 그대로 나온다.

### 새 규칙과 갈래 이름

- 품질 규칙 : `RuleStaleBasis = "stale-basis"` — 번호 **C14**, 단계 `StageLint`, 등급 `GradeCandidate`, 종목 `TypeStale`.
- 검토 갈래 : **새로 만든다.** `KindBasis = "basis"`, 화면 이름 「근거가 죽은 것」.

`stale` 에 안 넣는 까닭 : `ruleKind`(`review.go:52`) 표에서 `stale` 에는 이미 규칙 여섯(`stale-source-changed`·`unfixed-marker`·`stale-age`·`stale-conflict-pair`·`notation-drift`·`dead-path`·`dead-commit`)이 몰려 있다. 갈래 상한이 20줄이라 **새것이 밀려 안 보인다.** 사람이 「근거가 죽은 것만」 골라 볼 길도 있어야 한다.

`Kinds` 차례(`review.go:48`)는 `held → expired → basis → conflict → stale → …`. expired 다음이 맞다 — 근거가 죽은 것은 오래 둘수록 위험하다.

### 「그대로 둠」을 고르면 매번 다시 뜨는 문제

**`stale_after` 를 다시 쓴다.** 사람이 `mem set Y --stale-after 2026-12-31` 을 치면 그날까지 basis 큐에서 뺀다. 새 칸을 안 파는 대신, 그날이 오면 `expired` 큐로 와서 한 번 더 눈에 든다. 「미룬 것을 영영 잊지 않는다」가 공짜로 따라온다.

## 4. `mem show X` — 「나를 근거로 삼은 기억」 절

### 화면 (md)

`model.Encode(memory)` 뒤에 덧붙인다.

```
## 나를 근거로 삼은 기억 (3건)

- 20260828-1111  근거  decision  2026-08-28  `공유기를 모델 M 으로 바꾼다`
- 20260829-2222  링크  history   2026-08-29  `설치 기록`
- 20260830-3333  근거  fact      2026-08-20  `옛 회선 속도` (이미 무효)
```

- **0건이면 절을 통째로 안 찍는다.** 대부분의 기억이 0건이라 매번 빈 절이 나오면 화면만 는다.
- 색인이 없거나 `--no-index`·`--from-archive` 면 안 찍는다. 이 절은 곁다리라 못 찍는다고 명령이 실패하지 않는다.
- 제목은 `safe.Summary` 를 지난다 — show 출력은 그대로 AI 문맥으로 들어간다 (불변조건 I3 · `cmd_show.go:109 neutralized` 와 같은 이유). `--raw` 면 씻지 않는다.
- 차례는 날짜 오름차순, 같으면 id 순 (`review.sortItems` 와 같다).

### `--json`

최상위에 `used_by` 배열을 더한다.

```json
{"id":"20260822-aaaa","type":"decision", … ,
 "used_by":[{"id":"20260828-1111","by":"source","type":"decision","date":"2026-08-28","title":"공유기를 …","live":true}]}
```

`by` 는 `"source"`(sources 의 `mem:`) 또는 `"link"`. 둘 다면 `"source"`.

**`model.Memory` 에는 칸을 안 더한다.** 그 구조체는 md 머리말로 그대로 나가는 것이라, 파생값을 넣으면 언젠가 파일에 샌다. `cmd_show.go` 안에서만 쓰는 껍데기를 만든다.

```go
// showJSON 은 화면에 낼 것만 담는다. model.Memory 를 그대로 품어 칸 이름이
// 지금과 같고, used_by 는 색인이 만든 파생값이라 파일에 안 나간다.
type showJSON struct {
	*model.Memory
	UsedBy []index.UsedByRow `json:"used_by,omitempty"`
}
```

## 5. `mem review` 에서 사람이 판정하는 흐름

기존 UI 를 그대로 쓴다 — `Item.Why` 한 줄, `Related` 한 줄, `Next` 여러 줄 (`review.Markdown`).

```
## 근거가 죽은 것 (2건)

- 2026-08-28 20260828-1111 `공유기를 모델 M 으로 바꾼다`
    근거 `mem:20260822-aaaa` 가 2026-08-30 에 덮였다 (덮은 것은 20260830-bbbb)
    같이 볼 것 : 20260822-aaaa 20260830-bbbb
    → mem show 20260828-1111                        (아직 맞는 말인지 본다)
    → mem set 20260828-1111 --by <새id>             (덮였으면 — 새 기억을 먼저 넣는다)
    → mem set 20260828-1111 --invalid-at 2026-08-30 (덮을 새 기억 없이 그냥 틀렸으면)
    → mem set 20260828-1111 --stale-after <날짜>    (아직 맞다 — 그날 다시 본다)
```

사람이 고르는 셋이 그대로 세 줄이다.

| 사람의 판정 | 치는 명령 | 그 뒤 |
| --- | --- | --- |
| **덮음** | `mem add … --by 20260828-1111` 또는 `mem set … --by <새id>` | 이 기억이 죽고, **이 기억을 근거로 삼은 것들이 다음 판 큐에 온다** (연쇄가 한 칸 구른다) |
| **무효** | `mem set … --invalid-at <날짜>` | 죽는다. 대신 들어올 새 기억이 없을 때 |
| **그대로 둠** | `mem set … --stale-after <미래 날짜>` | 그날까지 큐에서 빠지고, 그날 `expired` 로 온다 |

링크로만 걸린 것은 `Why` 문구가 다르다 : ``이 기억이 `links` 로 가리킨 20260822-aaaa 가 2026-08-30 에 덮였다. 근거로 쓴 것인지 본다``.

## 6. 색인 변경

### 새 질의 — `internal/index/basis_queries.go`

```go
// UsedByRow 는 이 기억을 근거·링크로 가리킨 기억 하나다.
type UsedByRow struct {
	ID    string `json:"id"`
	By    string `json:"by"`   // "source" | "link"
	Type  string `json:"type"`
	Date  string `json:"date"`
	Title string `json:"title"`
	Live  bool   `json:"live"`
}

// UsedBy 는 이 기억을 sources 의 `mem:` 이나 links 로 가리킨 기억이다.
// superseded_by 는 안 본다 — 그것은 「덮은 것」이지 근거가 아니다.
func (d *DB) UsedBy(id string) ([]UsedByRow, error)
```

SQL 은 UNION 둘 :

```sql
SELECT m.id, m.type, m.title, m.summary, m.created_at, m.invalid_at, m.superseded_by, 'source'
  FROM sources s JOIN memories m ON m.id = s.mem_id
 WHERE s.kind = 'mem' AND s.value = ? AND m.id <> ?
UNION ALL
SELECT …, 'link'
  FROM links l JOIN memories m ON m.id = l.src
 WHERE l.dst = ? AND m.id <> ?
```

`sources` 표는 접두를 뗀 값을 담는다 (`rows.go:270` — `kind='mem'`, `value='20260822-aaaa'`). `mem:` 은 순수 id 만 허용이라(`validate.go` `IsSource`) 값이 깨끗하다. Go 쪽에서 같은 id 가 둘 나오면 `source` 를 남긴다. 열 이름은 구현 때 `rows.go` 의 실제 정의를 보고 맞춘다 (`date` 열이 아니라 `created_at` 이다).

### 인덱스 둘

```sql
CREATE INDEX ix_links_dst ON links(dst);
CREATE INDEX ix_src_mem   ON sources(value) WHERE kind = 'mem';
```

`links` 는 `PRIMARY KEY(src, dst)` 라 `dst` 로 찾으면 훑기다. `sources` 는 인덱스가 하나도 없다 — `schema.go:142~144` 가 **「표는 남기고 인덱스만 뺐다. 읽는 질의가 생기면 그때 다시 붙인다」**고 적어 둔 그 자리다. 옛 `ix_src_kind` 가 20k 에서 1.25MB 였는데, `kind='mem'` 부분 인덱스는 `mem:` 근거만 담아 훨씬 작다.

### 마이그레이션 — **없다**

`SchemaVersion` 을 4 → 5 로 올리기만 한다 (`schema.go:34`). 판이 다르면 `OpenRebuilding`(`schema.go:258`)이 파일을 지우고 통째로 다시 만든다 — 색인은 파생물이다(설계 6-2). 사용자가 칠 명령은 없고, 다음 `mem` 명령이 알아서 다시 만든다. 저장소가 크면 그 한 번이 오래 걸리니 **릴리스 노트에 적는다.**

`Docs/Guide/색인스키마.md` 도 같이 고친다.

### review 는 색인을 안 쓴다

한 번 더 못 박는다. `mem review --kind basis` 는 md 만 읽는다. `index.db` 를 지워도 큐가 그대로 나온다.

## 8. 시험 계획

### 단위 — `internal/quality` (경계 열하나)

| # | 무엇 | 기대 |
| --- | --- | --- |
| 1 | **연쇄** — X 죽음, Y `sources: mem:X`, Z `sources: mem:Y` | Y 만 걸린다. Z 는 안 걸린다 |
| 2 | **자기참조** — Y 의 `links` 에 Y 자신 | 안 걸린다 |
| 3 | **이미 무효인 기억** — Y 의 `invalid_at` 이 지났다 / `superseded_by` 가 있다 | 둘 다 안 걸린다 |
| 4 | **덮은 쪽** — Y 의 `superseded_by == X` 이고 X 가 죽었다 | 안 걸린다 (근거가 아니다) |
| 5 | **sources 접두가 다른 것** — `file:20260822-aaaa` · `note:mem:20260822-aaaa` · `url:…` | 안 걸린다. `mem:` 만 걸린다 |
| 6 | **근거가 살아 있다** — X 에 `superseded_by`·`invalid_at` 둘 다 없다 | 안 걸린다 |
| 7 | **덮은 것 없이 무효** — X 는 `invalid_at` 만 지났다 | 걸린다 |
| 8 | **스누즈** — Y 의 `stale_after` 가 미래 / 과거 | 미래면 안 걸리고, 지났으면 걸린다 |
| 9 | **링크로만** — Y 의 `links` 에만 X | 걸리되 `Why` 가 「링크」 문구다 |
| 10 | **없는 id** — Y 가 `mem:20260101-ffffffff` 를 가리키는데 그 기억이 없다 | basis 는 안 걸린다 (D01 `dead-mem-link` 자리다) |
| 11 | **상한** — basis 21건 | 20줄 + 「못 본 것」 한 줄 |

### 단위 — `internal/index` 둘

12. `UsedBy` 가 links·sources 를 다 모으고, 둘 다인 기억을 한 번만 `by:"source"` 로 낸다.
13. `SchemaVersion 4` 로 만든 색인이 새 exe 에서 통째로 다시 만들어진다 (`TestSchemeChangeRebuilds` 꼴 그대로).

### 명령 — `cmd/mem` 둘

14. `mem set X --by Y` 화면에 「근거로 삼은 기억 N건」이 뜬다. 0건이면 안 뜬다. 색인이 없으면 「못 셌다」가 뜬다.
15. `mem show X --json` 에 `used_by` 가 있고, **원본 md 파일에는 `used_by` 칸이 안 생긴다** (파일을 읽어 확인).

### 골든 시나리오 하나

```
A  decision  «공유기는 모델 M 이다»
B  fact      sources: [mem:A]
C  history   links:   [B]

1) mem add --type decision … --by A      → 화면 : A 를 근거로 삼은 기억 1건 : B
2) mem index
3) mem review --kind basis               → B 한 건. C 는 안 뜬다 (2단이라 안 본다)
4) mem show A                            → 「나를 근거로 삼은 기억 (1건)」 절에 B
5) mem set B --by <새 D>                 → 화면 : B 를 근거로 삼은 기억 1건 : C
6) mem index && mem review --kind basis  → 이번엔 C. 사람 판정으로 연쇄가 한 칸 굴렀다
7) mem set C --stale-after 2027-01-01
8) mem review --kind basis               → 볼 것이 없다
```

## 9. 소단계와 공수

**눈금 근거** — `Docs/History/공수기록.md` 「mem 종류 표 vocab.toml 분리 + fact 종류 추가 (2026-08-30)」의 배운 것 : **「설계에서 표·시그니처까지 정하면 구현 벽시계는 사람 눈금의 약 1/4」** (예상 9시간 15분 → 실제 3시간 38분). 같은 문서 v0.4 회차의 **「설계가 문장까지 정한 갈래는 눈금 ×0.7」**, SoundTool 회차의 **「실측이 든 소단계는 눈금을 그대로 둔다」**.

이 설계는 SQL·구조체·시험 목록까지 적었으므로 아래 「벽시계」 칸은 사람 눈금 ÷ 4 다. 다만 8번은 실측이라 안 줄였다.

| 소단계 | 사람 눈금 | 벽시계 예상 |
| --- | --- | --- |
| 1. `quality` — 역참조 표 만들기 + C14 규칙 + `rules.go` 등록 | 60분 | 15분 |
| 2. `review` — `KindBasis` · `Kinds` 차례 · `kindName` · `ruleKind` · `nextFor` | 40분 | 10분 |
| 3. `index` — `UsedBy` · 인덱스 둘 · `SchemaVersion` 5 | 50분 | 13분 |
| 4. `cmd_show` — 역참조 절 · `--json used_by` | 45분 | 12분 |
| 5. `cmd_set`·`cmd_add` — 화면 두 줄 · i18n 키 셋 | 30분 | 8분 |
| 6. 시험 15개 + 골든 시나리오 | 90분 | 25분 |
| 7. 문서 — `mem help set/review/show` · `Docs/Guide/명령명세.md` · `색인스키마.md` | 30분 | 8분 |
| 8. 빌드 · 설치 · 실사용 확인 (**실측이라 안 줄인다**) | 45분 | 45분 |
| **합** | **약 6시간 30분** | **약 2시간 15분** |

조사 3절이 눈대중으로 잡은 「1번 3~4시간 + 4번 1~2시간 = 4~6시간」과 사람 눈금이 맞는다. 조사 6절이 **「역참조 색인이 이미 있으면 훨씬 싸진다」**고 적었는데, 실제로 `sources` 표가 이미 있고 `LinkTargets`(`search_queries.go:410`) 꼴도 있어 3번이 싸다.

## 11. 정한 것 / 못 정한 것

### 정한 것

| # | 무엇 | 어떻게 |
| --- | --- | --- |
| 1 | 근거의 범위 | `sources` 의 `mem:X` + `links` 의 X. `superseded_by=X` 는 뺀다 |
| 2 | 자기참조 · 이미 무효인 기억 | 뺀다 |
| 3 | 전파 깊이 | **1단만.** 연쇄는 사람 판정으로 한 칸씩 |
| 4 | 상태를 어디 두나 | **아무 데도 안 둔다.** review 가 md 를 훑어 매번 계산한다 |
| 5 | 새 규칙 | `stale-basis` (C14 · `StageLint` · `GradeCandidate`) |
| 6 | 새 검토 갈래 | `--kind basis` 「근거가 죽은 것」. `stale` 에 안 섞는다 |
| 7 | 갈래 차례 | `held → expired → **basis** → conflict → stale → value → cold → link → title` |
| 8 | `set --by` 가 하는 일 | 화면 두 줄만. 파일·큐에 새로 쓰는 것 0 |
| 9 | 「그대로 둠」 | `--stale-after` 재사용(스누즈). 새 칸 0개 |
| 10 | `show` 출력 | 0건이면 절을 안 찍는다. `--json` 은 `used_by` |
| 11 | `model.Memory` | 안 건드린다. `cmd_show` 안의 껍데기 구조체로 푼다 |
| 12 | 색인 | `UsedBy` + 인덱스 둘 + `SchemaVersion` 5 (통째로 다시 만들기, 이전 코드 0) |
| 13 | 훅 | 안 건드린다 |

### 못 정한 것 — 사용자 판단이 필요하다

1. **`links` 를 근거로 볼 것인가.** 넣는 쪽으로 설계했지만 오탐이 늘 수 있다. **실제 저장소(301건)에서 `--kind basis` 를 한 번 돌려 건수를 보고 정하는 것을 권한다.** links 몫이 너무 많으면 빼거나 `--kind basis-link` 로 가른다.
2. **스누즈를 `stale_after` 재사용으로 할지, 새 칸을 팔지.** 재사용을 권한다(칸 0개). 다만 `stale_after` 는 원래 「다시 볼 날 예약」이라 뜻이 조금 겹친다.
3. **색인 다시 만들기 비용.** `SchemaVersion` 5 는 모든 사용자의 `index.db` 를 한 번 다시 만든다. 301건이면 순간이지만 20k 면 몇 분이다. 다른 스키마 변경과 묶어 한 번에 낼지.
4. **`mem show` 역참조 절을 기본으로 켤지, `--used-by` 옵션 뒤에 둘지.** 기본 켜기를 권한다(대개 0~3건이라 화면이 안 넘친다).
5. **basis 큐의 기본 상한.** 지금 값 20 을 그대로 쓸지, 급한 갈래라 더 크게 잡을지.

## 13. 구현 때 설계와 달라진 것 (2026-08-30)

| 무엇 | 설계 | 구현 | 왜 |
| --- | --- | --- | --- |
| basis 큐의 「다음에 칠 명령」 | 넷 (`show` · `--by` · `--invalid-at` · `--stale-after`) | **셋 — `--invalid-at` 줄을 뺐다** | `model.Validate` 가 `superseded_by` 와 `invalid_at` 을 **한 짝**으로 본다. `mem set <id> --invalid-at <날짜>` 만 주면 관문이 종료 코드 2 로 거절한다 (실제로 쳐서 확인). 못 치는 명령을 큐에 적으면 안 된다 |
