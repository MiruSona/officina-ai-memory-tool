# AIMemoryTool v0.4 설계

작성 2026-08-24 · 4회차 2단계(설계) · **백지 재설계가 아니다.** v0.3 을 그대로 두고 그 위에
**「검색 + 문서 품질」 두 기둥짜리 작은 회차**를 얹는다. 읽은 것은 조사 A(`../Research/2026-08-24-조사A-v0.0~v0.3비교.md`) ·
요청 원문 · v0.3 설계 1·8·13·18절 · v0.3 진행상황 4·5절 · 최종측정 · 측정절차 · v0.3 코드다.

> **한 줄 요약** — v0.4 의 목표는 **「자를 넘긴다」가 아니라 「천장을 밀어 올릴 길이 실제로 있는지 재서 답한다」** 다.
> G1 r@5 0.761 과 G6① DUP 0.750 은 둘 다 **지금 장치의 천장**이고, 천장을 넘으려면 G2 나 G6② 를 깨야 한다.
> 그래서 이번 판은 **① 열 가중이 뜻대로 듣게 고치고(C2) ② DUP 을 벡터가 아닌 길로 밀어 보고
> ③ 규칙 쪽을 세게 하고 ④ 되돌릴 수 있는 속도 후퇴를 되돌리고 ⑤ 작은 구멍 다섯을 닫는다.**
> **못 밀면 자를 옮기지 않고 「이 장치의 천장은 여기다」를 문서에 못 박고 실사용으로 넘어간다.**

## 2. 갈래별 설계

### ① C2 — `HeadField` 에서 태그·scope 를 가른다

**무엇을** — 지금 `HeadField` 는 `제목 + 태그 + scope` 를 한 글자열로 이어 붙여 FTS5 의 `head_s` 한 열에 넣는다.
그래서 태그가 열 개 붙은 기억은 **제목 낱말이 그 열 안에서 묽어진다.** 열 가중 16/6/1 은 「제목이 가장 무겁다」는
뜻인데 실제로는 「제목+태그+scope 덩어리가 무겁다」로 들린다. **이것을 두 열로 가른다.**

**어느 파일**

| 자리 | 무엇을 |
| --- | --- |
| `internal/index/rows.go:100-114` | `HeadField` 를 **`TitleField`(제목만) + `MetaField`(태그+scope)** 둘로 가른다. `HeadNM`(정규화 열)도 같은 글로 만든다(`:113`) |
| `internal/index/rows.go:226` | `memories` 삽입과 `fts_ko`·`fts_en`·`fts_norm` 삽입에 열 하나를 더한다 |
| `internal/index/schema.go:128-133` | `fts_ko`·`fts_en`·`fts_norm` 을 **4열**(`title_s`·`meta_s`·`summary_s`·`body_s`)로. `SchemaVersion` 3 → **4** (`schema.go:32`) |
| `internal/index/search_queries.go:72-88,115-117` | `fieldWeights` 를 `[3]float64` → `[4]float64`. `SetFieldWeights` 의 **「0 이하가 섞이면 안 받는다」 고삐는 그대로 둔다** |
| `internal/index/rows.go:93-99` (`Lens`) · `internal/search/rerank.go` | 재순위 bm25 의 길이 정규화가 같은 네 열을 봐야 짝이 맞는다 |
| `internal/config/config.go` (`search.field_weights`) | 칸이 네 값을 받게. **옛 `mem.toml` 이 세 값이면 넷째를 기본값으로 채우고 경고 한 줄** (모르는 값을 조용히 넘기지 않는다 — 불변조건 7) |

**어떻게 재나**

1. `index --full` 을 다시 돌린 뒤 **골든셋 3벌(v2 80 공식 · 손 30 · 42) × 두 모드**로 `eval`. 절차는 v0.3 `Docs/Guide/측정절차.md` 4절 그대로.
2. **열 가중은 스윕해서 고른다.** 제목/메타/요약/본문 넷을 격자로 재고 **v2 80건 r@5 가 가장 높은 자리**를 고르되,
   **G2(abstain 1.000 · 오배제 ≤ 0.02)를 못 지키는 자리는 후보에서 뺀다**(결정 3).
3. **이전 전(`repoA`)·이전 후(`repoM`)를 둘 다 잰다** — C2 는 「`migrate` 가 검색을 나쁘게 하던 원인」으로 지목된 자리라
   **이전 후 값이 올라가는지가 이 갈래의 진짜 증거**다.

**성공/실패 판정**

| | 판정 |
| --- | --- |
| **성공** | v2 80 r@5 가 0.761 보다 **오르고** G2 가 1.000/0.000 그대로 · ko/en 격차 ≤ 0.15 유지 |
| **부분** | r@5 는 그대로인데 **이전 후 값이 오르거나** 손 30 낱말 오배제 0.042 가 내려간다 → 채택하고 「검색 점수는 안 올랐다」를 적는다 |
| **실패** | r@5 가 내려가거나 G2 가 깨진다 → **되돌린다.** 스키마 판도 3 으로 되돌린다 |

### ② DUP 0.750 을 올리는 벡터 아닌 길

**무엇을** — 지금 DUP 은 **1단(후보 좁히기) → 2단(확정)** 두 단이다.
1단은 simhash 밴딩 + 요약 지문 밴드 + 문장 조각 지문 + 태그·scope 겹침(`similar.go:220-260`),
2단은 닮음 점수 S 와 **사실 대조**(`facts.go` — 숫자·이름이 어긋나면 안 잡는다)다.
**놓친 것이 1단에서 후보로도 안 올라온 것인지, 2단에서 걸러진 것인지부터 가른다.**

**차례 (이 차례를 지킨다)**

| 순 | 무엇 | 왜 먼저 |
| --- | --- | --- |
| 1 | **놓친 DUP 을 1단/2단으로 가른다** — 골든셋 DUP 짝마다 「후보에 올랐나 / S 가 얼마였나 / 사실 대조에 걸렸나」를 찍는다 | **고칠 자리가 어디인지 모르는 채 문턱만 만지면 v0.3 의 0.917 예측이 또 난다** |
| 2 | 1단이 원인이면 **후보를 넓힌다** — ⓐ 요약 지문 밴드(`sumBands`)의 밴드 수·해밍 거리 ⓑ 문장 조각 지문(`sketch`)의 조각 하한 `minUnitLen 12`·상한 `maxUnits 48` ⓒ **문자 n-gram MinHash 시그니처를 후보원으로 더할지** (8절 조사 보강) | 후보에 없으면 2단이 아무리 좋아도 못 잡는다 |
| 3 | 2단이 원인이면 **사실 대조를 다듬는다** — 숫자·날짜·고유명사가 「어긋난다」의 판정을 좁힌다(같은 뜻의 다른 표기를 어긋남으로 세고 있지 않나) | 「거짓 경보 0」을 지키는 것이 바로 이 2단이라 **약하게 만들면 G6② 가 깨진다** |
| 4 | **문턱은 마지막에** — `dup_reject 0.08` · `dup_warn 0.06` 은 **재서 정한다**. 안 움직여도 된다 | v0.3 이 「문턱으로는 못 가른다」를 이미 배웠다 |

`facts.go`(2단 사실 대조) · `idf.go`(무게). **`vectors.go` 는 안 건드린다**(결정 10).

**성공/실패 판정** — 측정절차 5절 그대로 `mem eval --quality --repo <품질 저장소 130건 사본> --golden <quality.yaml>`.

| | 판정 |

| **실패** | 위 넷 중 하나라도 깨진다 → **되돌리고 「0.750 이 이 장치의 천장이다」를 문서에 못 박는다.** 이것도 이번 판의 답이다 |

## 3. 구현 계획 — 갈래 나눔

**규칙은 `CLAUDE.md` 「갈래를 나눠 병렬로 돌릴 때」 그대로다** — 한 패키지는 한 갈래만 고치고,
공용 파일은 **줄을 더하기만** 하고, 남의 자리는 **「넘긴 것」 표에 적어** 뒷정리가 합친다.

### 3-1. 갈래 표

| 갈래 | 소유 패키지·파일 (여기만 고친다) | 공용 파일 (줄 더하기만) | 의존 | 예상 |
| --- | --- | --- | --- | --- |
| **A. C2 열 가르기** | `internal/index/**` · `internal/search/rerank.go` | `internal/config/config.go` (`field_weights` 칸) | 없음 | **180분** (스키마 +30 · 가중을 **재서 정한다** ×2) |
| **B. 문서 품질** (② DUP → ③ 규칙, **한 갈래가 이 차례로**) | `internal/quality/**` | — | 없음 | **②180 + ③100 = 280분** |
| **C. 속도** (④) | `internal/lint/**` · `cmd/mem/cmd_lint.go`·`cmd_review.go`·`cmd_status_v2.go` | — | **C1(계측)은 처음부터 · C2(고침)는 B 가 끝난 뒤** | 계측 60 + 고침 120 = **180분** |
| **D. 작은 것 다섯** (⑤) | `cmd/mem/cmd_index.go`·`cmd_set.go`·`cmd_eval.go` · `internal/eval/goldenset.go` · README·`Guide/` | `internal/config/config.go` (`[embed] model` 칸) | 없음 | **90분** |
| **뒷정리** | 합치기 · 전체 빌드·`go vet`·`go test -count=1 ./...` · 동결 | — | 넷 다 뒤 | **150분** (갈래 4 × 30 + 여유) |

**왜 ②·③ 을 한 갈래로 묶었나** — 둘 다 `internal/quality` 다.
v0.3 에서 2C·2D 가 같은 패키지를 나눠 가졌다가 **직렬이 됐고 측정이 오염됐다**(공수기록 「배운 것」 ②).
같은 실수를 안 한다 — **한 갈래가 ② 다음 ③ 을 한다.**

**왜 C 를 둘로 쪼갰나** — `lint` 시간의 큰 몫이 `internal/quality` 안(문장 정렬)에 있다.
**계측(C1)은 코드를 안 고치니 처음부터 병렬로 돌 수 있고**, **고침(C2)은 갈래 B 가 `quality` 를 놓은 뒤**라야 한다.
C1 이 만든 **규칙별 시간 표는 갈래 B 에게도 넘긴다** — B 가 후보를 넓힐 때 그 표를 보고 판단한다.

**`internal/config/config.go` 가 유일한 공용 파일이다** (A 가 `field_weights`, D 가 `[embed] model`).
**서로 다른 절이라 줄만 더하면 안 부딪힌다.** 부딪히면 뒷정리가 합친다.


**병렬 기준 벽시계 약 13시간.** v0.3 이 11시간이었고 그 판은 **임베딩을 새로 붙인 판**이었다.
이번 판은 **고치는 일**인데도 비슷한 것은 **「값을 재서 정한다」가 갈래 셋에 들어 있어서**다(눈금 ×2 · 9절).

## 4. 시험 계획

**v0.3 `Docs/Guide/측정절차.md` 를 그대로 쓴다.** 새 절차를 만들지 않는다 — v0.3 이 「절차를 틀리면 값이 통째로 달라진다」를

### 4-1. 그대로 하는 것

| 무엇 | 절차 |
| --- | --- |

### 4-2. 이번 회차가 **더** 재는 것 둘

| 무엇 | 왜 | 어떻게 |
| --- | --- | --- |
| **새 규격(`migrate` 뒤) 20k 로 `index.db` 다시 재기** | 58.25MiB 는 **낙관적**이다. `title`·`sources` 를 채우면 늘고 여유가 3% 뿐이다. **게다가 C2 가 FTS5 열을 하나 더 만든다** | 20k 가데이터에 `migrate --apply` 를 돌린 벌을 하나 더 만들고, `index --full` 뒤 `status --db`. **옛 규격 값과 나란히 두 줄** |

- **동결 exe 하나로 다 잰다.** 크기와 **SHA-256** 을 재서 시험 문서 머리에 적고, 그 뒤로 코드를 한 줄도 안 고친다.

- 끝나고 `git status Memory/ .claude/ AIMemoryTool/v0.1 v0.2 v0.3 Docs/` 가 **비어 있어야** 한다.

## 8. 조사 보강 (웹)

**WebSearch 로 두 주제를 짧게 봤다.** 아래 넷만 쓸 만했다. **어느 것도 이번 판에서 「채택」이 아니다 —
2절이 정한 「재서 정한다」의 후보**다.

| 무엇 | 요지 | 이 툴에 적용 · 비용 · 걸림돌 | 출처 |
| --- | --- | --- | --- |
| **MinHash + LSH 로 후보 좁히기** | MinHash 가 SimHash 보다 미묘한 차이를 잘 가른다. **후보를 넓게 뽑고 뒤에서 정밀 필터**를 거는 2단 구조가 실무 표준 | **갈래 ② 1단의 후보원 후보.** 이미 있는 한글 바이그램을 시그니처로 재활용할 수 있어 부피는 열 하나. **다만 100자 미만 짧은 글은 shingle 이 모자라 Jaccard 추정이 부풀려진다** — 기억 1건이 딱 그 크기다. **실측으로 확인** | [In Defense of MinHash Over SimHash](https://arxiv.org/pdf/1407.4416) · [Near-duplicate Detection with LSH](https://yorko.github.io/2023/practical-near-dup-detection/) |
| **숫자·고유명사·날짜 불일치 감점** | **이 주제를 정면으로 다룬 실무 자료를 못 찾았다.** 인접 자료에서 「필드별 문자열 거리 조합」과 「LSH 로 뽑고 후처리 규칙으로 거짓 경보를 거른다」는 2단 원칙만 확인된다 | **근거가 얇다.** 감점 계수를 참고할 공식이 없어 **골든셋으로 직접 정해야 한다.** 비용은 정규식 추출이라 거의 0. **실측으로 확인** — 지금 코드의 `facts.go` 가 이미 이 자리다 | [Detecting Near-Duplicates for Web Crawling (Manku, Google)](https://research.google.com/pubs/archive/33026.pdf) |
| **문장 정렬** | 문장 길이 수열·용어 위치를 견주는 방식이 지문 방식보다 정밀도가 높다. 한 사례가 **최소 중첩 25% 에서 정밀도 1.00 · 재현율 0.93** | **v0.3 이 이미 쓰고 있다**(`align.go`). 새로 넣을 것이 아니라 **다듬을 자리**다. **후보 좁힌 뒤에만 돌려야 한다**(전수는 그대로 `lint` 시간이 된다 — 지금 43%가 이것이다). 한글 문장 분리가 허술하면 정렬이 흔들린다. **실측으로 확인** | [Exploiting Sentence-Level Features for Near-Duplicate Detection](https://link.springer.com/content/pdf/10.1007/978-3-642-04769-5_18.pdf) |
| **BM25F — 제목/태그/본문 열 가중** | 제목 매치가 본문 매치보다 관련성이 높다는 것은 정설. **열마다 길이 정규화가 따로 걸려 짧은 제목의 매치가 더 크게 실린다** | **갈래 ① 을 그대로 뒷받침한다.** SQLite FTS5 의 `bm25(table, w1, w2, …)` 가 이미 하는 일이라 **엔진 기본 기능만으로 된다.** 색인 한 번 다시 만들면 조회 비용은 같다. **걸림돌 거의 없음 — 넷 중 가장 확실하다** | [Keeping it boring (and relevant) with BM25F — Sourcegraph](https://sourcegraph.com/blog/keeping-it-boring-and-relevant-with-bm25f) |

**안 가져온 것 둘**

| 무엇 | 왜 |
| --- | --- |
| **한글 동의어 사전(우리말샘 · 낱말 워드넷)** | **라이선스와 대량 내려받기 가능 여부를 확인 못 했다.** 「무료 라이선스만」이 요청 원문의 제약이라 확인 전에는 못 쓴다. 게다가 **일반 도메인 사전이라 게임 개발 용어를 못 잡는다** — 지금의 `[canon]` 사람 표가 그 자리다 |
